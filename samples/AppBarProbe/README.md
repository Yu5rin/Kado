# AppBarProbe — AppBar 成立性の検証

要件書 2 章「ドック時の画面分割」が本当に成立するかを確かめるための最小 WPF アプリ。
本プロジェクト最大の技術リスクなので、Core と並行して先に検証する。

確かめたいのは 1 点だけ。

> **ピン留めすると画面端にワークエリアが確保され、他のウィンドウを最大化しても重ならないこと。**

## 実行

Windows でのみ動作する（`net8.0-windows` / WPF）。

```
dotnet run --project samples/AppBarProbe
```

## 検証手順

### 1. 画面分割が成立すること（完了条件 3）

1. AppBarProbe を起動する。
2. 辺（左／右）と幅を選び、**［ピン留めする］** を押す。
3. ログに登録前後のワークエリアが出るので、**幅の分だけ狭まっている**ことを確認する。
4. エクスプローラーやメモ帳など別のウィンドウを開き、**最大化**する。
5. 最大化したウィンドウが AppBarProbe に**重ならない**ことを確認する。
6. **［ピンを外す］** を押し、最大化中のウィンドウが画面いっぱいに広がることを確認する。

あわせて次も確認しておくとよい。

- タスクバーと同じ辺に置いても、`ABM_QUERYPOS` の調整結果に従って共存すること
- 動画などを全画面表示すると最背面へ退避し、終了後に復帰すること（`ABN_FULLSCREENAPP`）
- タスクバーの位置や自動的に隠す設定を変えると、追従して再配置されること（`ABN_POSCHANGED`）

### 2. 異常終了から復旧すること（完了条件 4）

`ABM_REMOVE` を呼ばずにプロセスが落ちると、**ワークエリアが削られたまま残りデスクトップが壊れる。**
安全装置が効いていることを 2 経路で確認する。

**例外で落ちた場合（安全装置 1）**

1. ピン留めした状態で **［わざと例外を出す］** を押す。
2. エラーダイアログが出た時点で AppBar が解除され、ワークエリアが戻っていることを確認する。

**強制終了された場合（安全装置 3）**

> **注意：タスクマネージャの「プロセス」タブから終了しても異常終了にはならない。**
> この経路はウィンドウにまず `WM_CLOSE` を送るため、アプリ側の終了処理が走って
> AppBar は正常に解除される（控えも消える）。本当に強制終了するには次のどちらかを使う。
>
> - タスクマネージャの **「詳細」タブ** で `AppBarProbe.exe` を選んで「タスクの終了」
> - コマンドプロンプトで `taskkill /F /IM AppBarProbe.exe`

1. ピン留めした状態にする。
2. 上記のいずれかで **強制終了** する。この経路は例外ハンドラを通らないため、
   ワークエリアが削られたまま残る。
3. デスクトップのワークエリアが狭いままであることを確認する（壊れた状態の再現）。
   画面端に他のウィンドウを最大化すると、空白の帯が残っているのが分かる。
4. AppBarProbe を**もう一度起動**する。
5. 起動直後のログに「前回の異常終了を検知しました」と出て、**ワークエリアが復旧している**
   ことを確認する。復旧の前後の矩形もログに出る。

正常に終了した場合は「前回は正常に終了しています」と出る。どちらが起きたかログで
判別できるので、手順どおりに再現できているかはここで確かめられる。

> ### 実機で分かったこと（Windows 11 / 1920x1080 / 100%）
>
> **Windows が自動でワークエリアを戻す。** `TerminateProcess` 相当で確実に落としても、
> 3 回とも再起動時にはワークエリアがフル画面に戻っていた。Explorer が死んだウィンドウの
> AppBar 登録を破棄し、ワークエリアを再計算しているものとみられる。
>
> **`SPI_SETWORKAREA` でワークエリアを削ることはできない。** 検証のために意図的に
> 削ろうとしたが、設定した値がそのまま無視された（設定後に読み直すと元の値）。
> `SPIF_SENDCHANGE` で飛ばした `WM_SETTINGCHANGE` を受けた Explorer が、
> タスクバーを基準に再計算して上書きしているとみられる。
>
> この 2 つの結果、**この環境では「ワークエリアが削られたまま残る」状況を再現できず、
> 安全装置 3 の単独での実効性は検証できなかった。** 一方で、完了条件である
> 「強制終了させても再起動時にワークエリアが復旧する」は満たされている。
>
> 安全装置 3 は保険として残す。Windows の自動復旧は仕様として保証されたものではなく、
> バージョンやタイミング、他の AppBar の有無によって変わりうるため。なお復旧方向
> （本来の値に戻す向き）は Explorer が戻そうとする向きと一致するので、削る向きより
> 通りやすいと考えられる。

**確実に異常終了を再現する（安全装置 3 の検証）**

1. ピン留めした状態で **［解除せずに強制終了する］** を押す。
   確認ダイアログで OK を押すとプロセスが即座に終了する（`TerminateProcess` 相当なので
   解除処理も例外ハンドラも通らない）。
2. デスクトップの端に帯が残り、ウィンドウを最大化しても届かないことを確認する。
   Windows 側が自動で戻してしまう場合は、この時点で帯が無い。
3. もう一度起動し、「前回の異常終了を検知しました」と出て**ワークエリアが戻る**ことを
   確認する。

> **`SPI_SETWORKAREA` は通知ありだと効かないことがある。** 実機で確認した挙動で、
> `SPIF_SENDCHANGE` を付けると `WM_SETTINGCHANGE` を受けた Explorer がタスクバーを
> 基準に再計算し、設定した値を即座に上書きしてしまう。そのため書き戻しは、通知ありで
> 効かなければ通知なしで試し直し、結果をログに出すようにしてある。

控えは `%LOCALAPPDATA%\Kado\appbar-probe.state.json` に置かれる。
ピン留め中だけ存在し、正常に解除すると消える。

**二重起動が止まること（安全装置 2）**

1. 起動したまま、もう一度 `AppBarProbe.exe` を起動する。
2. 「すでに起動しています」と出て 2 つ目が立ち上がらないことを確認する。

## 実装のポイント

| ファイル | 役割 |
|---|---|
| `AppBarController.cs` | `ABM_NEW` → `ABM_QUERYPOS` → `ABM_SETPOS` での登録、`ABM_REMOVE` での解除、通知への追従 |
| `WorkAreaRecovery.cs` | 安全装置 3。登録前のワークエリアを控え、次回起動時に書き戻す |
| `App.xaml.cs` | 安全装置 1（例外ハンドラ 2 経路）と安全装置 2（ミューテックス） |
| `Interop/NativeMethods.cs` | `SHAppBarMessage` ほかの P/Invoke |

- 通知用メッセージ ID は `RegisterWindowMessage` で確保し、`HwndSource.AddHook` で受ける
- `ABM_QUERYPOS` が返す矩形は他の AppBar との調整後の値なので、**希望値のまま `ABM_SETPOS` に渡さない**
- ドック中は `WindowStyle=None` / `ResizeMode=NoResize` にする（要件書 7.2）。枠があると
  ドロップシャドウの分だけ画面端との間に隙間が見える
- **隣のウィンドウとの隙間**は、こちらの配置がぴったりでも残る。隣接するウィンドウが
  ドロップシャドウ用の不可視マージンを持つためで、Windows でウィンドウを並べたときの
  標準的な見た目（タスクバーと最大化ウィンドウの間に隙間が無いのは、タスクバーが
  特別扱いされているから）。常駐アプリでは目につくので、ウィンドウだけを数ピクセル
  はみ出させて埋められるようにした（「隙間埋め」）。AppBar に申告する矩形は変えないので、
  他のウィンドウの最大化範囲には影響しない
- ただし**この量は固定にできない**。スナップ配置の隣接ウィンドウは影のマージンを持つが、
  最大化されたウィンドウは可視境界がワークエリアにぴったり揃うため隙間が無く、
  同じ量だけはみ出させると<b>重なってしまう</b>。「他のウィンドウを最大化しても重ならない」は
  最優先の要件なので、隣が最大化されている間は隙間埋めを休止する。最大化は AppBar の
  通知に乗らないため、ドック境界の外側にあるウィンドウを Z 順で特定して定期的に見張っている
- さらに `DWMWA_EXTENDED_FRAME_BOUNDS` で実際の可視境界を測り、ウィンドウ矩形との差だけ
  外側に広げて配置する。Windows 10 以降は `GetWindowRect` の矩形に不可視のマージンが
  含まれるため、素直に置くと端まで届かない
- 復旧時は `SPI_SETWORKAREA` の前にダミーの AppBar を登録・解除して、Explorer に
  ワークエリアを再計算させる。死んだウィンドウの登録が残っていると書き戻しが効かないことがある
- DPI は マニフェストで `PerMonitorV2` を宣言。AppBar は物理ピクセルでやり取りするため、
  ウィンドウの移動も WPF の座標系ではなく `SetWindowPos` で行う

## 本番への移植

ここで確かめた実装は Phase 5 で `Kado.Shell` に移す。
その際は次を追加する（要件書 2.2）。

- ドック幅のドラッグ変更と `ABM_SETPOS` の再交渉（ドラッグ中は間引く）
- ドック状態・辺・幅・対象モニタの保存と復元
- `WM_DISPLAYCHANGE` でのモニタ構成変更への追従
