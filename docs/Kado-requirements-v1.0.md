# Kado 要件書 v1.0

**Kado** — Windows デスクトップアプリ（C# / .NET 10 / WPF）として新規に作る、予定とタスクの管理ツール。
リポジトリは `github.com/Yu5rin/Kado`。
既存のEdge拡張 inaCalendar v1.19.3 は**機能の参考**として扱い、UI・操作系・情報設計は一新する。

---

## 1. プロダクトの位置づけ

一日中画面に置いたまま使う常駐型の予定・タスク管理ツール。Googleカレンダー／Googleタスクと同期しつつ、
**会社の実働日（稼働日）を軸に日数を数えられる**ことが他製品との差になる。UI/UXは製品版相当を目標とする。

### 1.1 既存実装からの引き継ぎ

引き継ぐのは以下のロジックのみ。UI層はすべて捨てる。

| 引き継ぐ | 理由 |
|---|---|
| 繰り返し判定（`recurMatches` / `buildRule`） | 仕様が固まっており作り直す価値がない |
| 実働日変換（`workingDaysToDiff` / `diffToWorkingDays` / `toRanges` / `expandRange`） | 本アプリの中核。挙動を変えてはいけない |
| Google同期アルゴリズム（差分同期・tombstone・relink・重複除去） | 事故対応の積み重ねが入っている。簡略化すると同じ事故を踏む |
| 内蔵実働日データ（2023年〜） | 初期投入データとして流用 |

引き継がないもの：ビューごとの表示項目ON/OFF設定、タスクを予定のフラグとして持つデータモデル、
設定パネルの構成、ポップアップ前提の窮屈な情報設計。

### 1.2 技術スタック

| 項目 | 選定 |
|---|---|
| ランタイム | .NET 10（LTS） |
| UI | WPF（フルネイティブ。WebView2は使わない） |
| 配布 | 単一exe（self-contained, win-x64） |
| データ保存 | SQLite（Microsoft.Data.Sqlite + Dapper） |
| Google連携 | Google.Apis.Calendar.v3 / Google.Apis.Tasks.v1 |
| Excel読込 | ClosedXML |
| 通知 | Windowsトースト（不可時はトレイのバルーンにフォールバック） |
| シェル統合 | Win32 P/Invoke（SHAppBarMessage 他） |

### 1.3 プロジェクト構成

```
Kado.sln
├ Kado.Core     … 繰り返し・実働日・日付計算。UI非依存、単体テスト対象
├ Kado.Data     … SQLiteリポジトリ、マイグレーション、バックアップ/復元
├ Kado.Google   … Calendar/Tasks 同期、OAuth、トークン保護
├ Kado.Shell    … AppBar、ホットゾーン、トレイ、通知（Win32集約）
└ Kado.App      … WPF本体（View / ViewModel）
```

## 2. 最重要要件：ドック時の画面分割

**本アプリを画面端に留めたとき、他のウィンドウを最大化しても重ならないこと。** 本プロジェクトで最も優先度が高い要件であり、
ここが満たせなければ他の機能が揃っても目的を達しない。実装順でも最優先の検証対象とする（9章参照）。

### 2.1 モード遷移

```
ウィンドウ ──[端へドラッグ / ホットキー]──> オーバーレイ ──[ピン]──> ドック
                                            <──[ピン解除]──
```

| 状態 | ワークエリア | 他ウィンドウとの関係 |
|---|---|---|
| オーバーレイ | 削らない | 最大化したウィンドウの**上に重なる** |
| ドック（ピン留め） | **削る** | 最大化しても**重ならない**（画面分割が成立） |

Windowsの仕様上、自動非表示AppBarはワークエリアを削らないため、ホバー表示のままでは重なりを避けられない。
出入りのたびにAppBarを登録・解除すれば理屈の上では可能だが、そのたびに全ウィンドウがリサイズされて実用にならない。
したがって**「ホバーで呼び出し、ピンを押すと画面分割に切り替わる」**という2段構えを正式な仕様とする。

### 2.2 ピンの挙動

- ヘッダのピンボタンで切り替える。ピン留め中はホバー判定を止め、常時表示のままにする
- ピン留め時に `ABM_NEW` → `ABM_QUERYPOS` → `ABM_SETPOS` を実行し、ワークエリアを確保する
- ピン解除時に `ABM_REMOVE` を実行し、ワークエリアを元に戻す
- ドック幅はドラッグで変更でき、変更のたびに `ABM_SETPOS` で再交渉する
- ドック状態・辺（左右）・幅・対象モニタは終了時に保存し、次回起動時に復元する
- `ABN_FULLSCREENAPP` を受けたら一時的に退避し、全画面アプリの終了後に復帰する
- タスクバーや他社製AppBarと同じ辺に共存する場合は、`ABM_QUERYPOS` の調整結果に従う

### 2.3 安全装置（必須）

`ABM_REMOVE` を呼ばずにプロセスが落ちると、**ワークエリアが削られたまま残りユーザーのデスクトップが壊れる**。
以下3点を必ず実装する。

1. `AppDomain.UnhandledException` と `DispatcherUnhandledException` の両方で AppBar を解除する
2. ミューテックスで二重起動を防止する（AppBarの多重登録を防ぐ）
3. 起動時に前回の異常終了を検知し、`SPI_SETWORKAREA` でワークエリアを復旧する

## 3. データモデル

### 3.1 予定とタスクは完全に分離する

**Core / Data 層では別テーブル・別同期経路で保持し、統合はViewModel層のみで行う。**
Google Calendar と Google Tasks が別APIである以上、ここを混ぜると同期のたびに変換が入り不整合の温床になる。
またタスクは「期限だけある」「いつやるか未定」という状態を持つ必要があり、開始・終了時刻が前提の予定と同じ型には収まらない。

```
Event    … 開始日時／終了日時／終日フラグ／場所／繰り返し／カレンダーID／色／メモ
Task     … タイトル／期限日（任意）／完了フラグ／タスクリストID／メモ
           ＋ 作業時間ブロック（任意：日付＋開始時刻＋所要時間）
Milestone … 日付／種類名（取り込んだ文字列）／取り込み元バージョン
            読み取り専用。編集不可、Google非同期
```

タスクの「作業時間ブロック」は**タスク側の属性**であり、予定には変換しない。
UI上は週・日ビューの時間軸に置かれるが、データとしてはタスクのまま（表示も点線枠で区別する）。

### 3.2 保存先

`%LOCALAPPDATA%\Kado\data.db`（SQLite）。検索は FTS5 を使う。
リフレッシュトークンは DPAPI（`ProtectedData.Protect`、CurrentUserスコープ）で暗号化して別ファイルに保存。

## 4. 実働日の扱い

### 4.1 データ供給とファイル形式

会社から配布される Excel（例：`実働日ファイル.xlsx`）を正とする。供給経路は3つ。

1. 内蔵データ（初期投入）
2. Excelファイル読み込み（ClosedXML）
3. フィード配信（URLから自動取得）

#### 取り込むファイルの構造

| 位置 | 内容 | 扱い |
|---|---|---|
| 1〜3行目 | バージョン（例：Ver.25.1）、参照先パス、ファイル名 | バージョンを取り込み履歴に記録し、更新判定に使う |
| B列（5行目以降） | 稼働日の日付 | **稼働日として登録** |
| C列 | 実働日の通し番号 | 読み飛ばす（アプリ側で再計算） |
| D列 | マイルストーン名称 | **同じ行の日付のマイルストーンとして登録** |
| A列 / L〜N列 | 連番、別系統の稼働日リスト（2002年〜） | 今回は使わない |
| E〜J列 | 「計算データー」区分別リードタイム表 | 今回は使わない |

#### 取り込み規則

- 5行目以降を走査し、B列に日付があればその日を稼働日として登録する
- 同じ行のD列に文字列があれば、その日のマイルストーンとして登録する
- **マイルストーンの名称は固定4種と決め打ちせず、D列に現れた文字列をそのまま種類として登録する。** 将来名称が増えても取り込みが壊れない。色は種類ごとに自動割り当てし、設定で変更できる
- **既存データは全置換せず、ファイルに含まれる期間だけを置き換える。** 稼働日とマイルストーンは期間が異なる（例：稼働日 2023/1/5〜2026/3/31、マイルストーン 2025/1/10〜2026/3/26）ため、それぞれの期間で判定する。期間外の既存データは残す。古いファイルを誤って読み込んでも過去データが消えないようにするため
- フィード取得時はヘッダのバージョンを比較し、上がっていれば差し替える

祝日は内閣府の公開CSVを取得。**Shift_JISなので `Encoding.RegisterProvider(CodePagesEncodingProvider.Instance)` が必須。**

### 4.2 マイルストーン

実働日データと一緒に取り込まれる**読み取り専用のレイヤー**。予定でもタスクでもない第3のデータ種別として持つ。

- 現行データでは 仕様期限 → 1次GO → S中日程 → M中日程 の4種が1セットで、**連続する稼働日に並び、月におよそ3サイクル**回る
- 編集・削除はできない。Googleにも同期しない（ローカルのマイルストーンテーブルに保持）
- 表示は種類ごとの固定色ラベル

#### 配色（固定）

| 種類 | 色 | ライト（面 / 文字） | ダーク（面 / 文字） |
|---|---|---|---|
| 仕様期限 | 黄 | `#faedc4` / `#7a5600` | `#4a3a14` / `#e8cd7e` |
| 1次GO | 赤 | `#f6ddda` / `#8f2f28` | `#4a2320` / `#f0b3ad` |
| S中日程 | 緑 | `#d7ebe0` / `#1f6347` | `#1d3d30` / `#8fd3b4` |
| M中日程 | 青 | `#dde6f4` / `#1f4a83` | `#1f3352` / `#a9c8ee` |

棒・帯として描くときの実色は 仕様期限 `#d0a017` / 1次GO `#b3453c` / S中日程 `#2f7d5b` / M中日程 `#2b5fa8`。
名称が増えた場合は、この4色に続く系列から自動割り当てし、設定で変更できる。

#### 表示位置

| ビュー | 表示方法 |
|---|---|
| 月 | 日付番号を左に固定し、**その右に残る領域でラベルを中央寄せ**（縦に並んだとき位置が揃う） |
| 週・日 | 日付ヘッダにラベル |
| 一覧 | 日付列にラベル |
| 年（ストリップ） | 日付の**上に横棒**（1マスが約10pxで文字が入らないため） |
| 年（カレンダー） | 日付の上に色帯 |
| 右ペイン | 選択日ヘッダにラベル |

### 4.3 カレンダー上の表示

- 非稼働日は色を足さず背景を沈める。祝日の赤や予定の色と競合させないための引き算
- ツールバーに「今月の実働日 ◯日 ／ 残り ◯日」を常時表示
- **実働日の通し番号**は、ツールバーのサマリー・右ペインの選択日ヘッダ・一覧ビューの日付列・週ビューの日付ヘッダに表示する。月ビューのセルと年ビューには出さない（マイルストーン表示と競合し、密度が上がりすぎるため）

### 4.4 期限の数え方

タスクの期限は実働日で数える。

| 条件 | 表示 |
|---|---|
| 実働日データがある範囲 | 「残り 3実働日」 |
| データが無い範囲（翌年度など） | 「残り 189日」（単位を落として暦日表記。ツールチップで未登録である旨を補足） |
| 期限当日 | 「今日まで」 |
| 超過 | 「3実働日 遅れ」（赤） |

境界規則は**今日は数えず、期限日は数える**で統一。
期限日そのものが非稼働日だった場合は、**直前の実働日に寄せて計算し、寄せた結果を明示する**（例：「残り 2実働日（9/25まで）」）。

### 4.5 実働日計算パネル

期間→実働日数、基準日＋N実働日→到達日の2機能。ワンクリックで開くパネルとして実装し、常設はしない。
ウィンドウモードではサイドパネル下部のボタン、サイドバーモードではフッターのボタンから開く。
カレンダー上のドラッグでも期間を選択できる。

## 5. UI仕様

### 5.1 3つの表示モード

| モード | 挙動 |
|---|---|
| ウィンドウ | 通常のリサイズ可能ウィンドウ。全ビュー利用可 |
| オーバーレイ（自動非表示） | 画面端にマウスを当てるとスライドイン。他ウィンドウの上に重なる |
| ドック（ピン留め） | 画面端に常駐し、ワークエリアを削って他ウィンドウと重ならない |

モード遷移とドック時の画面分割の仕様は2章を参照。
幅によってレイアウトを切り替える。同じUIを縮小して使い回さない。

### ビュー構成

**月・週・日・年（ストリップ）・一覧（アジェンダ）の5つ。**

- **年ビューは年度単位（4月〜翌3月）**で、2形式を持つ
  - **ストリップ**（既定）… 1行1か月、横に1〜31日を並べる。会社配布の実働日カレンダーと同じ形で、休みの並びと繁閑が縦に揃って読める。右端に月の実働日数。月末以降は枠を作らず空ける（2月なら28日で打ち切り）
  - **カレンダー** … ミニカレンダー12枚。日付を引き当てる用途
  - 切り替えは**年ビュー内のアイコンボタン**（横線3本／カレンダーマーク）で行う。**設定画面には出さない**。状態は記憶する
- 上期・下期は行のグルーピングで示すため、**半期ビューは設けない**（ストリップに吸収）
- 一覧（アジェンダ）は予定とタスクを時系列で流す。**予定のない日と休みは、連続分をまとめて1行に畳む**（完全に消さず、日付の連続性は保つ）。一般的なカレンダーアプリは予定のない日を非表示にするが、実働日の感覚が飛ぶのを避けるための折衷

### 5.2 ウィンドウモード（3ペイン構成）

```
┌──────────────────────────────────────────────┐
│ ☰  2026年9月  ◀ ▶ 今日 │月 週 日 半期 年│ 実働20/残6   検索  同期  ⚙ │
├────────┬──────────────────────┬────────────┤
│ ミニ月暦   │                        │ 選択日ヘッダ    │
│ カレンダー一覧│   本体ビュー              │ （実働◯日目）   │
│ タスクリスト │   （月／週／日／半期／年）    │ ───────── │
│          │                        │ 予定 3        │
│ 実働日計算  │                        │ ───────── │
│          │                        │ タスク 3/4     │
└────────┴──────────────────────┴────────────┘
```

- **左サイドパネルは折りたたみ可能**。ツールバー左端のボタンで開閉し、閉じると中央が広がる。状態は終了時に保存して次回復元。初回は開いた状態
- 閉じても情報が欠けないよう、実働日サマリーはツールバー側に置く
- 右ペインは予定とタスクを上下に**同時表示**（幅があるためタブにしない）
- ビュー切替はツールバーのセグメント一本に統一する

### 5.3 サイドバーモード（幅約352px）

上にカレンダー、下に予定／タスクの**タブ切替**。この幅で上下に分けると各ペインが3行しか入らず実用にならないため。
仕切りはドラッグで高さを変更できる。実働日計算はフッターのボタンから下からせり出す。

### 5.4 タイムブロッキング

週・日ビューの上部に終日レーンを置き、終日予定と期限付きタスクを並べる。
**タスクを時間軸へドラッグすると作業時間ブロックが確保される。** ブロックは点線枠で予定と視覚的に区別する。

> **決定（実装しない）**: 上記のうち「タスクを時間軸へドラッグして作業時間ブロックを
> 確保する」操作は実装しないことに決めた。テーブル・モデル・リポジトリ・描画の分岐
> まで一通り用意したが、作る導線（ドラッグ操作そのもの）が最後までひとつも実装
> されなかったため、利用者と相談のうえ見送りとした。導線の無いコードは落としてある。
> データベースの `work_blocks` テーブルだけは、マイグレーションを増やさないために
> 定義を残してある（詳しくは `docs/README.md` の「作業時間ブロック（`work_blocks`）は
> 実装しないと決めた」を参照）。終日レーンと期限付きタスクの表示は本文どおり実装済み。

### 5.5 設定項目の削減

現行のビュー別表示項目ON/OFF（5ビュー × 5項目）は廃止する。本来デザインで解くべき問題であり、
これがあるために設定パネルが4画面分に膨らんでいた。設定はおおむね1/3に削り、レイアウトの作り込みで代替する。

残す設定：テーマ（light/dark/auto）、週開始曜日、表示時間帯、通知（事前通知・日次サマリー）、
カテゴリ管理、カレンダーの表示切替と並び順、実働日データの供給元、起動時の表示モード、自動起動。

### 5.6 デザイントークン

| 用途 | ライト | ダーク |
|---|---|---|
| 背景 / パネル | `#fbfbfc` / `#ffffff` | `#1a1d24` / `#20242c` |
| 罫線 | `#e2e4ea` / `#c8ccd6` | `#2c313b` / `#3a4150` |
| 文字（主／副／補助） | `#1c2029` / `#585f6e` / `#8f96a4` | `#e6e9ef` / `#a8b0be` / `#727a89` |
| アクセント（藍） | `#27528f` / 面 `#e8eef7` | `#7aa5df` / 面 `#233247` |
| 日曜・祝日 / 土曜 | `#b03a34` / `#3b6ea8` | `#e0827c` / `#7aa5df` |
| 非稼働日の面 | `#eceef2` | `#171a20` |

フォントは Yu Gothic UI → Segoe UI。日付・時刻・日数は**すべて等幅数字（tabular figures）**で揃える。

## 6. Google連携

### 6.1 スコープ（現行踏襲）

```
calendar.events / calendar.readonly / calendar.app.created / tasks
```

### 6.2 認証

`chrome.identity` は使えない。Google Cloud Console で**「デスクトップアプリ」タイプのOAuthクライアントIDを新規発行**し、
ループバックリダイレクト方式に切り替える。拡張機能用のIDは流用不可。

### 6.3 同期で落としてはいけない処理

- 差分同期（syncToken）と全再同期の使い分け
- tombstone による削除伝播
- ローカル予定とGoogleイベントの再リンク
- 重複検出と除去
- 複数カレンダーの取得・表示ON/OFF・並び順
- Google標準色と自前パレットの相互変換
- 同期中の二重起動防止、バックグラウンド静音同期
- 日付・時刻の正規化（旧データのインポート経路に必須）
- 差分誤検知を防ぐJSON正規化（キーをソートして比較）

タスクはCalendarとは独立した同期経路を持つ。予定側の同期失敗がタスク側に波及しない設計にする。

## 7. デスクトップ固有の実装

### 7.1 画面端ホバー表示

画面端3〜5pxに `WS_EX_TRANSPARENT` の透明ホットゾーンを常駐させ、`WM_MOUSEMOVE` を検知してスライドイン。
**誤爆防止に150〜300msの滞留を条件にする。** アニメーションは150ms程度、`prefers-reduced-motion` 相当の設定に配慮する。

### 7.2 AppBar 実装メモ

仕様と安全装置は2章を正とする。実装時の補足のみ以下に置く。

- 通知用メッセージIDは `RegisterWindowMessage` で確保し、`HwndSource.AddHook` で受ける
- `ABM_QUERYPOS` が返す矩形は他AppBarとの調整後の値なので、希望値のまま `ABM_SETPOS` に渡さない
- ワークエリア変更は他プロセスのウィンドウ再配置を伴うため、幅変更のドラッグ中は `ABM_SETPOS` を間引く（確定時とドラッグ停止時のみ）
- ドックモードでは WPF 側の `WindowStyle=None` / `ResizeMode=NoResize` とし、リサイズは自前のグリップで扱う

### 7.3 マルチモニタ / DPI

`PerMonitorV2` をマニフェストで宣言。AppBarの登録先モニタは設定で選択。
`WM_DISPLAYCHANGE` でAppBar再登録とウィンドウ位置の再検証を行う。画面外に出た位置の補正処理は現行同等のものを用意する。

### 7.4 常駐とホットキー

閉じるボタンでトレイに格納。トレイメニューから表示モード切替、即時同期、設定、終了。
Windows起動時の自動起動オプション。`RegisterHotKey` でサイドバー呼び出しとクイック入力のグローバルホットキーを提供する。

### 7.5 通知

予定の事前通知、日次サマリー、タスクの期限通知。
非MSIX配布でトーストを出すには AUMID登録とCOMアクティベーターが必要なため、**不可の場合はトレイのバルーン通知にフォールバック**する設計にしておく。
スリープ復帰の取りこぼし対策として `SystemEvents.PowerModeChanged` で再スケジュールする。

## 8. データ移行

現行のバックアップJSONをインポートする移行ツールを**初回リリースに必ず含める**。
対象は予定・設定・同期状態・実働日データ。同期状態を引き継げれば再リンクが不要になり移行事故が減る。
引き継げない場合は初回に全再同期を走らせる。

移行時、**予定に付いていたToDoフラグはタスクへ変換する**。データモデルを分離したことによる唯一の変換処理であり、
ここは変換ログを残して結果を確認できるようにする。

## 9. 開発フェーズ

| Phase | 内容 | 完了条件 |
|---|---|---|
| 1 | Core（繰り返し判定・実働日計算・期限カウント）＋単体テスト | 既存JSと同じ入力で同じ結果。暦日フォールバックと非稼働日の丸めも網羅 |
| 2 | SQLiteデータ層＋旧JSONインポート（ToDo→タスク変換込み） | 現行バックアップが読み込め、変換ログが出る |
| 3 | WPF ウィンドウモード（月→週→日の順）＋予定・タスクCRUD＋Undo | 単独で予定とタスクの管理が完結する |
| 4 | Google同期（Calendar → Tasks の順） | 双方向同期・削除伝播・重複除去が動く |
| 5 | Shell統合（トレイ→サイドバーモード→ホバー→ピン／AppBar） | **2章の最重要要件を満たす**。ドックで画面分割が成立し、異常終了しても復旧する |
| 6 | 通知・フィード・祝日取得・バックアップ・年ストリップ・一覧ビュー | 現行機能を全て満たす |

**Phase 5 は最重要要件（2章）そのものであり、最大の技術リスクでもある。** Phase 1 と並行して、ピン留めでワークエリアが縮み、最大化した他ウィンドウが重ならないことだけを確認する最小プロトタイプを先に作る。ここが成立しない場合は設計を見直す。

## 10. Phase 1 の着手範囲

最初に書くのは `Kado.Core` の以下5つ。すべて単体テスト付き。

1. `WorkingDayCalendar` … 実働日集合の保持、稼働判定、月内通し番号の算出
2. `WorkingDayMath` … 期間→実働日数、基準日＋N実働日→到達日、暦日フォールバック
3. `DueDateFormatter` … 期限の残日数表記（実働日／暦日／今日まで／遅れ／非稼働日の丸め）
4. `RecurrenceRule` … 繰り返しルールの構築と判定
5. `WorkdayFileImporter` … 配布Excelの取り込み（稼働日＋マイルストーン、期間単位の置き換え、バージョン判定）

既存JSと同じ入力で同じ出力になることをテストで担保してから、上の層に進む。
