# 会社のネットワークで更新できない

対応した版: 次の版

会社の PC で「更新を確認…」を押すと「更新を確かめられませんでした。ネットワークをご確認ください。」
と出て、更新できない。同じ時点で GitHub の API は外からは正常に応答している。
失敗の理由はどこにも記録されておらず、そもそも追えなかった。

同じ作者の別アプリ **Pane で、同じ問題が実機のログで原因まで分かっている**ので、その方式に揃えた
（`Yu5rin/pane` の `docs/調査記録/修正-更新の失敗を追えるようにする.md`）。

## 原因（Pane の実機ログで分かったこと）

GitHub の API には、**未認証だと 1 時間に 60 回の上限**がある。上限は端末ごとではなく
**IP アドレスごと**に数えられるので、会社のように同じ出口を大勢で共有する回線では、
他の人の通信で先に使い切られる。Pane の実機ログでは、更新の確認が 5 回とも 403
（rate limit exceeded）で断られていた。自宅（専有の IP）では必ず成功する。

Kado も同じ作りだった。確認は API の `releases/latest` だけを見ていて、403 を
「ネットワークをご確認ください」に丸めていた。

## 直したこと

| 何を | どうした |
|---|---|
| 確認の順 | **Atom フィード（`releases.atom`）を先に見る。**上限の別枠なので、普段の確認は上限を受けない。Atom で最新版なら API には行かない |
| 新しい版があるとき | そこで初めて API へ、詳細（変更点の本文・添付の大きさ・SHA256）を取りに行く |
| API が 403 や障害のとき | 配布物の名前が決まっているので、`https://github.com/Yu5rin/Kado/releases/download/v{版}/Kado-{版}-win-x64.exe` を**組み立てて**落とす。SHA256 は分からないので照合は省く |
| 変更点が取れないとき | 更新の窓に「変更点を読めませんでした。リリースのページで確かめてください」を出す。リリースのページを開くボタンは元からある |
| 失敗の理由 | 確認・ダウンロードの各段階を `shell.log` に 1 行ずつ残す（下の表） |
| 利用者向けの文言 | 状況ごとに分けた（上限、プロキシ認証、時間切れ、接続できない、証明書、…）。例外の型名は出さない |
| 失敗したときの導線 | メッセージに「リリースのページを開きますか？」を添える |
| 通信を確かめる入口 | 設定の「Kado について」→「うまく更新できないとき」に置いた（下記） |

### 更新の窓が本文を読むこと（CLAUDE.md「リリース」）

窓が出す `ReleaseNotes` は API の `body` から来る。組み立てた URL で更新するときは
`body` を取れないので、`UpdateInfo.DetailsUnavailable` を立てて、窓が固定の文言
（変更点を読めませんでした）を出す。SHA256 の照合は元から本文を見ず、GitHub が添付ごとに
持つ `digest` を読むだけなので、その経路が無いときは省くだけで済む。

### 通信を確かめる入口

「更新できるようにする」修正を入れた版を会社の PC へ入れると、その時点で最新版になり、
更新するものが無いのでダウンロードが走らない。**診断する手段そのものが消える**
（Pane で実際に気づいたこと）。そこで、最新版でも押せる入口を置いた。

- Atom・API・配布ファイルの置き場に実際に接続する
- 配布ファイルは先頭の 256KB だけ受け取って切る。**保存しない**
- 結果（成功／状態コード／短い理由）を画面に出し、`shell.log` にも 1 行ずつ残す
- 配布ファイルの URL は、API を使わずに組み立てたもの（実際に API が使えないときに通る道）。
  最新のタグが分からなければ、いまの版のもの
- 中身の先頭が実行ファイルの形（`MZ`）でなければ「失敗」にする

## Pane から持ってきたもの / Kado 向けに変えたもの

**そのまま持ってきた考え方**

- Atom を先に見て、API は新しい版があるときだけ。API が失敗しても URL を組み立てて続行
- 並び順に頼らず、読めたタグのうち最大の版を選ぶ
- 例外の連鎖（`InnerException` すべて）と状態コードを 1 行に残す。応答の要点
  （状態・Content-Type・Via）、転送先、受信済みバイト数、プロキシ経由か（プロセスで 1 回）
- 利用者向けの文言を状況ごとに分ける（403 の文言は Pane と同じ趣旨）
- 407 への対処は入れない（下記）
- プレリリースについての注意書き（`AtomFeed` の説明に残した。Kado はプレリリースを使っていない）

**Kado 向けに変えたもの**

| 項目 | Pane | Kado |
|---|---|---|
| 配布物 | `Pane-{タグ}-win-x64.zip`（タグに `v` 付き） | `Kado-{版}-win-x64.exe`（版に `v` 無し。`release.yml` の `$exe`） |
| 置き場所 | `Pane/UpdateService.cs` に集約 | **通信の判断は `Kado.Presentation/Update/`**（Linux の CI でテストできる）。WPF 側の `UpdateService` は落として入れ替える側と記録の配線だけ |
| ログの出し先 | `Logger` | `ShellDiagnosticsLog`（shell.log）。Presentation は `log` コールバックを受けるだけ |
| Atom の ETag | 前回の ETag を設定に控えて 304 にする | **入れていない。**Atom は数十 KB で、確認は起動時と手動だけ。設定の置き場も要る。必要になれば後から足せる |
| タグの読み方 | 版として読めればよい（`-beta` の後ろは落とす） | **`vX.Y.Z` の形だけ**（数字 3 つ、各 5 桁まで）。それ以外は無視する。組み立てる URL に、応答から来た文字列をそのまま入れないため |
| XML | 既定（`XDocument.Parse`） | `DtdProcessing.Prohibit`・`XmlResolver=null`・文字数の上限を**明示**。DOCTYPE が付いていれば読まない |
| 大きさの上限 | 無し | Atom 1MB・API 2MB。ダウンロードは従来どおり読み取りの停止で切る |
| 許可ホストの検査 | 無し | **組み立てた URL も `ReleaseFeed.IsAllowedDownloadUrl` を通す。**リダイレクトも 1 回ごとに検査（`FollowAllowedRedirectsAsync` を Presentation へ移した） |
| 記録する URL | 最終 URL をそのまま | **クエリと資格情報を落とす。**転送先には `?sig=…` のような一時的な署名が付くため |
| ハッシュ無しの取得 | 警告して続行 | 続行するが、**Web ページ（`text/html`）と、先頭が `MZ` でないものは置かずに失敗**にする（下記） |
| Accept | 要求ごと | 同じ（以前は既定で JSON を要求していたのを直した） |

## 追加で入れた安全のこと

ハッシュを確かめられない取得（組み立てた URL）では、途中の中継が 200 で返したエラーページを
**そのまま exe として置いてしまう**恐れがある。`Apply` は「いまの exe を `.old` に改名 →
新しいものを置く → 起動」なので、HTML を置いて起動すると、アプリが起動できなくなる。
置く前に、`Content-Type` が `text/html` でないことと、先頭 2 バイトが `MZ` であることを確かめる。

## shell.log に出る行の例

`shell.log` はデータの保存先（設定の「データ」→ 保存先を開く）にある。
下は、会社の回線で API が 403 になったときの確認（テストで実際に出した行。時刻は省略）。

```
更新の確認: 開始（現在 1.0.4, 先に見る所=Atom）
更新の通信: プロキシを経由する（proxy.corp.example:8080, 宛先 github.com, 資格情報=なし）
更新の確認: Atom に問い合わせる https://github.com/Yu5rin/Kado/releases.atom
更新の確認: Atom 応答 200 OK, Content-Type=application/atom+xml; charset=utf-8, Content-Length=971, Via=(なし)
更新の確認: 新しい版がある（現在 1.0.4, 配布元 v1.0.5, 問い合わせ先=Atom）。詳細を API へ問い合わせる
更新の確認: API に問い合わせる https://api.github.com/repos/Yu5rin/Kado/releases/latest
更新の確認: API 応答 403 Forbidden, Content-Type=application/json; charset=utf-8, Content-Length=2, Via=(なし), X-RateLimit-Remaining=0
更新の確認: 失敗。HttpRequestException: 成功以外の状態コードが返りました [HTTP 403 Forbidden]
更新の確認: 新しい版（v1.0.5）はあるが詳細を取れなかった（RateLimited）。取得先を組み立てて続行する（SHA256の照合は省く）: https://github.com/Yu5rin/Kado/releases/download/v1.0.5/Kado-1.0.5-win-x64.exe
```

続けて「更新する」を押すと、ダウンロードの行が出る（`UpdateService.DownloadAsync`）。

```
更新のダウンロード: 開始 https://github.com/Yu5rin/Kado/releases/download/v1.0.5/Kado-1.0.5-win-x64.exe（想定 0バイト, SHA256=なし）
更新のダウンロード: 転送 302 → https://release-assets.githubusercontent.com/github-production-release-asset/…
更新のダウンロード: 応答 200 OK, Content-Type=application/octet-stream, Content-Length=…, Via=(なし)
更新のダウンロード: 転送先=https://release-assets.githubusercontent.com/github-production-release-asset/…
更新のダウンロード: 受信を終えた（…バイト）
更新の検証: リリースにハッシュが無いので確かめていません（通信は HTTPS で守られています）
```

## shell.log の読み方

`更新の確認:`（確認）、`更新の通信確認:`（「通信を確かめる」）、`更新のダウンロード:`、
`更新の検証:`、`更新の入れ替え:` で始まる。

| 出るもの | 意味 |
|---|---|
| `API 応答 403 Forbidden` と `X-RateLimit-Remaining=0` | **API の回数の上限。**共有回線ではよく起きる。Atom と組み立てた URL で更新はできる |
| `403` だが `X-RateLimit-Remaining` の行が無い | 上限ではなく、経路（プロキシ・フィルタ）で止められている疑い |
| `応答 407 ProxyAuthenticationRequired` と `Proxy-Authenticate=Negotiate/NTLM` | プロキシが認証を求めている。方式名が分かる（次の一手の手掛かり） |
| `Content-Type=text/html` | 中身が目的のものではなく、中継のエラーページ（`UnexpectedContentException`） |
| `転送先=` が出ない／転送前に失敗 | `github.com` は通るが、配布ファイルの実体（`*.githubusercontent.com`）が許可されていない構成 |
| `AuthenticationException` などの連鎖 | 社内の通信検査（TLS の差し替え）に引っかかっている |
| `SocketException` の連鎖 | 接続そのものができない（拒否・届かない・名前が引けない） |
| `TaskCanceledException` ← `TimeoutException` | 時間内に応答が無かった |
| `受信済み 0バイト` | 接続の時点で失敗 |
| `受信済み ○○バイト`（途中） | 大きいファイルが通らない、または途中で切られている |
| `更新の通信: プロキシを経由する（ホスト:ポート, …）` | プロキシ経由であること。起動ごとに 1 回。`資格情報=なし` なら、認証が要るとき通らない |
| `更新の確認: Atom を読めなかった。API へ問い合わせる` | Atom が使えなかった。API だけで確かめる（上限を受ける側） |
| `新しい版（…）はあるが詳細を取れなかった（RateLimited）…組み立てて続行する` | 上限を避けて更新に進んだ印 |

## 入れなかったもの（ログを見てから決める）

**プロキシ認証（407）への対処**（`DefaultProxyCredentials = CredentialCache.DefaultCredentials` など）
は入れていない。Pane と同じく、実機のログで 407 が出ていて、`Proxy-Authenticate` の方式が
Negotiate/NTLM だと分かってから決める。この版は **407 を見分けて、記録して、画面に出す**
ところまで。

## 実機でしか確かめられないこと

CI（Linux）では、通信を差し替えたテストで流れと文言までは固定している。次は実機で。

- 実際の会社の回線で「通信を確かめる」を押し、3 行の結果と `shell.log` を見る
- プロキシ経由の環境で、`更新の通信: プロキシを経由する（…）` が起動ごとに 1 回出るか
  （`HttpClient.DefaultProxy` は Windows のシステム設定・PAC を読む）
- API が 403 の状態で「更新する」まで進み、組み立てた URL で実際に落とせて入れ替わるか
  （本物の `release-assets.githubusercontent.com` への転送を含む）
- 転送先の URL に、署名（`sig=`）が `shell.log` に**出ていない**こと
- 更新の窓の「変更点を読めませんでした」の表示、失敗メッセージの「リリースのページを開きますか？」
- 設定の「うまく更新できないとき」の見た目（WPF は Linux で動かせず、XAML は組み立てを
  静的に検査しているだけ）

## 補足

- 公開ページ（`site/privacy.html`）の通信先の表は、更新の確認が `api.github.com` だけを
  挙げている。いまは `github.com`（`releases.atom`）へも行く。Google のブランディング欄に
  結びついた公開ページなので、この修正では触っていない。直すときは公開の手順（`site/README.md`）に従う
- `Apply` は `Process.Start` の失敗（`Win32Exception`）を捕まえない。置く前の `MZ` の検査で
  実際には起きにくくなったが、途中で失敗したときに元の版へ戻す道は、改名のあとの
  `IOException` などにしか効いていない
