### 要注意：要件書の中で食い違っている

**半期ビューを設けるか。**

| 箇所 | 記述 |

### モックと変えた3点

いずれもモックの見た目を保ったうえで、WPF 上で破綻しないようにした判断。

- **右ペインの予定とタスクをひとつのスクロールにまとめた。** モックは節ごとに
  独立したスクロール領域（`.dlist` が2つ）だが、WPF で高さを等分すると予定が
  少ない日に大きな空きができる。節が縦に続く見え方は変えていない
- **実働日バッジを「実働 N 日」と「残り N」の2つに分けた。** 残りは今日を含む月
  でしか出せないため。別の月を見ているときはバッジがひとつになる
- **まだ実装していないビューのセグメントは無効表示にした。** モックの
  `.seg button[disabled]` の見た目をそのまま使っている。押せるのに何も起きない
  よりは、押せないと分かるほうがよい

### モックに無いが実装で足したもの

- **元に戻す・やり直しはツールバーに出さず、Ctrl＋Z／Ctrl＋Y で受ける。**
  モックのツールバーにボタンが無いため、見た目を増やさずに機能だけ残した
- **同期の表示（`.sync`）は状態表示を兼ねる。** Google 同期は Phase 5 なので、
  いまは「Google 未接続」と出し、操作の結果があるときはそちらを出す。
  画面下に別のステータスバーを足すとモックの構成から外れる

### 左パネルの一覧の出どころ

「カレンダー」「タスクリスト」は `calendars` / `task_lists` の表から作る。以前は
予定の `calendar_id` とタスクの `task_list_id` から重複なく引いて組み立てていたが、
それだと名前も色も変えられず、予定が1件も無いうちは分類を先に作れなかった。

起動時に `CalendarWorkspace.EnsureSources()` が、予定やタスクが指している所属 ID を
表に起こす。足りないぶんだけ足すので何度呼んでもよく、旧 JSON を取り込んだあとにも
呼んでいる。表が空なら「マイカレンダー」と「マイタスク」を1つずつ作る。1つも無いと
予定の入れ先が決まらないため。

自分で作ったカレンダーの ID は `local:` で始まる（`local:9f1c…`）。名前とは別物なので、
名前を変えても予定の所属を付け替えなくてよい。そのぶん編集画面のカレンダー欄には
ID をそのまま並べられないので、`SourceChoice`（ID と名前の組）を渡し、`SelectedValuePath`
で ID を選ばせている。

削除するとき、中の予定やタスクは消さずに別のカレンダー／リストへ移す。分類を消した
かっただけなのに中身まで消えるのは行き過ぎなため。確認ダイアログには移る件数を出す。
最後の1つは消せない（`DeleteCalendar` が `null` を返す）。

色はカレンダーごとに決まり、予定1件ずつには持たせない。新しく作るときは
`CalendarPalette.NextColor` が既存と重ならない色を選ぶ。取り込み済みのものは Google 側の色、
それ以外は名前から決まる色なので、同じ名前には常に同じ色が付く。

## 編集画面（予定・タスク）

要件書にもモックにも編集画面は無い。ツールバーや右ペインで使っている部品の寸法
（枠 `1px` ／ 角丸 `5` ／ 高さ `28` ／ 見出し `11px` 補助色）に合わせて組んである。

項目は **Google Calendar / Google Tasks に合わせてある**。Phase 4 で同期を始めたときに、
こちらにしか無い項目・あちらにしか無い項目が出ないようにするため。

| 画面の欄 | 予定（Google Calendar） | タスク（Google Tasks） |
|---|---|---|
| タイトル | `summary` | `title` |
| 日付 | `start` / `end`（終日は日付、時刻付きは日時） | `due`（**日付のみ**。時刻を持たない） |
| 繰り返し | `recurrence`（RRULE） | なし（**Kado だけが持つ**。Google には送らない。下の「タスクの繰り返しも Kado だけの項目」） |
| 場所 | `location` | なし |
| URL | `source.url` | なし（**Kado だけが持つ**。Google には送らない。下の「タスクの URL と添付」） |
| 説明・詳細 | `description` | `notes` |
| 所属 | `calendarId` | タスクリスト |
| 完了 | なし | `status` |

Google Tasks の期限が日付だけなので、タスク側に時刻欄は置かない。

**色の欄は置かない。** 所属カレンダーで決まる（`ICalendarPalette`）。1件ずつ選ばせると、
左パネルの色見本と画面上の帯が食い違う。取り込んだ予定が持っている色は、上書きせず
そのまま残す。

### タスクの URL と添付は Kado だけの項目

Google Tasks の API には URL も添付の欄も無い。タスクに持たせた **URL と添付（ファイルやフォルダの
「場所」）は、手元（`tasks.url` / `tasks.attachments`、V12）にだけ持ち、Google には一切送らない**。
メモ（`notes`）に混ぜて送ることもしない（向こうで直したメモと食い違い、本文が汚れる）。

- 添付が持つのは場所（フルパス）だけで、ファイルの中身は持たない・上げない。`TaskAttachment` と
  JSON の行き来は `TaskAttachments`（`Kado.Data`）
- **同期で消えないことが要。** `TaskMapper.FromGoogle` は受け取るたびにタスクを作り直すので、
  `CreatedAt`・`SortOrder` と同じく `existing` から引き継ぐ。`TaskMapper.ToGoogle` には入れない
  （入れると `NeedsPush` が誤判定する）。`tests/Kado.Google.Tests/TaskLocalOnlyFieldsTests` が、取り込み・
  書き戻しの応答・新規送信の応答・引き受け・リスト移動のどれでも残ることを押さえている
- 検索の対象にはしない（予定の検索も `url` を見ていない）

### リンクと添付を開く

予定・タスクの右クリックメニューに「リンクを開く」「添付を開く」がある（編集の下）。開ける先が
無いときは項目ごと隠す。開く処理と安全確認は編集画面と共通で、`Kado.Presentation/Links` に集めてある。

- **開いてよい URL**（`LinkRules`）：リンクは http/https、予定の添付（Google ドライブ）は https だけ
- **ファイルの場所**（`PathLaunchPlanner`。起動しない純粋な関数）：フルパス（`C:\…`、`\\server\share\…`）だけ。
  フォルダはエクスプローラーで、ファイルはシェルで開く。**実行形式（.exe .bat .lnk など）は実行せず**、
  入っているフォルダを開いてそのファイルを選んだ状態にする。見つからなければ開かず「見つかりません：パス」
- 実際の起動は `ILinkOpener`（実物は `ShellLinkOpener`）。存在の確認は共有フォルダが落ちていると数十秒
  返らないので、別のスレッドで行う（`LinkLauncher.OpenPathAsync`）
- 右クリックの出し分けは `OpenTargets`（行の型ごとの振り分けは `OpenTargets.From`）。メニューの
  項目は `Themes/Controls.xaml` の `EventLinkMenuItemStyle`・`TaskLinkMenuItemStyle`・
  `OpenAttachmentMenuItemStyle`。**子メニューは別のポップアップで `ContextMenu` をたどれない**ので、
  子の項目のコマンドは `MainViewModel.AttachmentMenuItems` が項目に持たせる。メニューは全画面で共有する
  3種類にまとめてあるので、足し忘れる画面は出ない（次の「右クリックメニュー」。
  `tests/Kado.App.Tests/ContextMenuOpenItemsTests` が並びと使われ方を見張る）

### 右クリックメニュー（予定・タスク・日付と空き時間）

メニューは画面ごとに書かず、**`Themes/Controls.xaml` の共有の4つ**を全画面が参照する（以前は画面ごとに同じ並びを
書いていて、項目を1つ足すたびに足し忘れる画面が出た）。

| メニュー | 使う所 | 並び |
|---|---|---|
| `EventContextMenu` | 月のチップ・週と日の終日レーン・時間軸のブロック・一覧・右ペインの行・日付の行のラベル | 編集（編集できなければ「詳細を見る」）／リンクを開く／添付を開く／―／複製／別のカレンダーへ移す ▸／題名と日時をコピー／―／削除 |
| `TaskContextMenu` | 月のチップ・週と日の終日レーン・一覧 | 編集／完了にする・取り消す／期限を変える ▸／別のリストへ移す ▸／リンクを開く／添付を開く／―／複製／題名をコピー／―／削除 |
| `TaskRowContextMenu` | 右ペインのタスクの行 | 上と同じで、削除の上に「上へ移動／下へ移動」（区切り線で分ける） |
| `DayContextMenu` | 月のマスの空き・週の日見出し・週と日の時間帯の空き・年の日付・一覧の日付行・右ペインの空き | この日に予定を追加／この日にタスクを追加／―／この日を1日で見る／この週を見る／この月を見る（今いるビューと同じものは出さない） |

- **コマンドの引数は、右クリックされた行（`PlacementTarget.DataContext`）そのもの。** 行の型は画面ごとに違う
  （`EventChipViewModel`・`DayEventViewModel`・`TimeBlockViewModel`・`MilestoneViewModel`・`ScheduledTask`・
  `TaskListItemViewModel`・月のマス・年の日など）。どの行かの読み取りは `EntryRefs`（予定・タスクの識別子）と
  `DayTarget.From`（日付）が持ち、**識別子だけを取って、中身は保存されている行を読み直す**。コマンドと項目の
  出し分けは `MainViewModel.Menus.cs`
- **項目の出し分けは、項目自身の `DataContext` に置いた情報（`EventMenuInfo`・`TaskMenuInfo`・`DayMenuInfo`）で行う**
  （`OpenTargets` と同じ作り。コンバーターが `Tag` の本体と行から作る）。押せない項目は**隠さず灰色にして、理由を
  ツールチップに出す**（灰色にはツールチップが出ないので `ToolTipService.ShowOnDisabled`）。子メニューの項目は
  別のポップアップで `ContextMenu` をたどれないので、コマンドも押せるかも理由も `MenuChoice` が持つ
- **編集できない予定は「詳細を見る」**（読み取り専用の編集画面が開く。保存も削除もできない）。判定は
  `MainViewModel.EditBlockReason` ＝ 既存の `UnsendableMessage`（読み取り専用・Google から外れたカレンダー）と
  `EventMapper.IsLocked`（メールから作られた予約・誕生日・勤務場所・他人が主催する予定）。**Kado では表せない
  繰り返し（RDATE など）は含めない**（題・場所・メモなどは直せて、日時と繰り返しだけを編集画面が止める）。
  削除は既存の判断（`DeleteEventByCore`）のまま：Google 側で変えられない予定は削除できる、読み取り専用のカレンダーの
  Google から受け取った予定は削除できない
- **複製**は新しい予定を1件、同じ日・同じ時刻・同じカレンダーに作る（`CalendarWorkspace.DuplicateEvent`）。写すのは
  題名・場所・メモ・URL・色・通知だけ。**繰り返しは写さない**（繰り返しの1回分は、その日だけの単発になる）。添付・
  ゲスト・会議 URL・Google の結び付きは持たない（新規として送られる）。入れ先は、今のカレンダーに書き込めるなら同じ、
  読み取り専用などなら既定のカレンダー（実働日の入れ先は取り込みで消えるので避ける）。タスクの複製は未完了・親なし
- **移す**は、編集画面でカレンダー（リスト）を変えて保存したときと同じ経路（入れ先の希望だけを書き換え、
  Google 側の `events.move`／`tasks.move` は同期が行う）。移せない理由（`EventMapper.MoveBlockReason`・
  `TaskMapper.MoveBlockReason`）は子メニューの項目ごとに灰色にして出す。移し先の候補は編集画面の候補と同じ決まり
  （`CalendarChoicesFor`／`TaskListChoicesFor`）から今のものを除く。並びと色は左パネルと同じ
- **期限を変える**は、ドラッグで期限を動かしたときと同じ経路（`CalendarWorkspace.SetTaskDue` → `UpdateTask`）。
  「次の稼働日」「来週の週始め」は `TaskDuePresets`（今日・週の始まり・稼働日の判定を外から受ける純粋な関数）が決め、
  稼働日は `CalendarWorkspace.Workdays`（`WorkdayRule`）。期限なしにすると繰り返しも外れる（`TaskRepeating.Normalize`）
- **コピー**は `IClipboard`（実物は `WpfClipboard`。クリップボードを他のアプリが握っていると失敗するので
  `TrySetText` が false を返し、「コピーできませんでした」と出す）。文面は `EntryText`
- **全部 Undo できる編集**（`Edits.cs`。複製は `AddEventEdit`／`AddTaskEdit`、移す・期限は `UpdateEventEdit`／
  `UpdateTaskEdit`。説明文だけ言い分ける）
- **時間帯の時刻**：メニューは右ボタンを離したときに開くので、押した時点で `TimelineColumnView` が、押した高さの時刻
  （15分に丸める）を添付プロパティ `DayMenu.Time` に控え、メニューがそれを読む
- **予定・タスクの上で右クリックしたときに日付のメニューが出ない**のは、WPF が `ContextMenu` を持つ**いちばん内側の
  要素**のメニューを開いて、そこで止める（`Handled`）ため。外側（マス・列・行）の日付のメニューには届かない。
  予定・タスクの要素には必ず自分の `ContextMenu` を付ける（メニューを付ける要素は `Tag` に `MainViewModel` を入れる）
- **ショートカットの表示（`InputGestureText`）は付けていない。** メニューに出す操作のうち、キーに対応するのは
  右ペインで行を指しているときの Delete だけで、全画面で共有するメニューには書けない（複製の Ctrl＋D などは無い）

### タスクの繰り返しも Kado だけの項目

Google Tasks の API には繰り返しの欄が無い（Google のアプリで付けた繰り返しは、外からは読めも作れもしない）。
そこで **Kado 独自の繰り返し** を、手元（`tasks.repeat`、V13）にだけ持つ。Google には送らない。
**完了にすると、Kado が「次の回」を新しいタスクとして作り**、それがふつうのタスクとして Google に送られる。

- **種類は8つ**。暦どおりの4つ（毎日・毎週◯曜日・毎月◯日・毎年◯月◯日）は RRULE の形
  （`FREQ=WEEKLY;BYDAY=MO`）で、**期限日から曜日・日付を決めて明示して持つ**。稼働日基準の4つ
  （毎週の週始め・週終わり、毎月の月初・月末）は RRULE で表せないので独自の書き方
  （`X-KADO=WEEK-FIRST-WORKDAY` など）。読み書きと次の回の計算は `Kado.Core.Recurrence.TaskRepeat`
  （純粋な関数。`NextDue`）、タスクを組み立てる決まりは `Kado.Data.Models.TaskRepeating`
- **次の期限は「今の期限より後」かつ「今日以降」のいちばん早い該当日**。溜めてから完了しても過去の回は作らない
- **毎月・毎年は、無い日を月末に寄せる**（31日 → 2月は28日。次の月は31日に戻る）。RFC 5545 の `BYMONTHDAY`
  は日の無い月を飛ばすので、この2つは `RecurrenceRule` を使わず自前で数える。毎日・毎週は `RecurrenceRule`
- **稼働日**は `WorkdayRule`：登録した稼働日データ（`WorkingDayCalendar`）がある期間はそれが決め、登録の無い期間は
  土日と祝日（`JapaneseHolidays`）を除いた日。**週の区切りは設定の「週の始まり」**。稼働日が1日も無い週・月は飛ばす
- **読めない指定は「繰り返さない」として扱い、次の回は作らない。文字列は消さない**（編集画面には
  「読めない指定のまま」と出る）
- **付けられないのは、期限の無いタスクとサブタスク**。編集画面では選べなくし（理由を出す）、保存でも外す
  （`TaskRepeating.Normalize`）。期限日が変わったら暦どおりの指定は新しい期限日で指定し直す（ドラッグでの移動も）

完了にしたときの流れ（`CalendarWorkspace.ToggleTask` / `UpdateTask`。チェック・チップ・編集画面の保存のどれでも同じ）：

1. そのタスクを完了にし、**繰り返しを外す**（取り消して完了し直しても二重にならない）
2. 次の回を作る（題名・メモ・リスト・URL・添付・繰り返しを引き継ぎ、期限は求めた日。Google の結び付きは持たない）

この2つが**1つの元に戻せる操作**（`CompositeEdit`）。元に戻すと完了と繰り返しが戻り、次の回が消える（Google と
結び付いたあとなら、既存の削除の流れで墓標を残して Google からも消える）。完了の取り消しでは何もしない。

**Google 側で完了にされたとき**は、`TaskSyncEngine` が受け取りの前後を見比べる。手元では「未完了で繰り返しあり」
だったものが「完了」になっていたら、同じ決まりで次の回を作る。次の回は受け取りのあとの**送信で、同じ同期のうちに**
Google に新規として作られる。同じ完了をもう一度受け取っても、繰り返しはもう外れているので作らない。同期は画面とは別の
接続で動くので、稼働日と週の始まりは次の回が要るときにだけ読む（`RepeatEnvironment`）。作ったことは **`SyncReport.Notes`**
（警告ではなく知らせ）に1行残す（件数は `CreatedLocal` に入る）。`Warnings` に入れると同期の表示が毎週のように
「一部を伝えられません」になって邪魔なので、警告の表示・「確認した」の流れには載せず、同期のあと下のステータスに
「同期しました。繰り返しの次の回を作りました：題名 10/13(月)」と一度だけ出す（`MainViewModel.AnnounceSyncNotes`）。

**同期で消えないことが要。** `TaskMapper.FromGoogle` は `existing` から引き継ぎ、`ToGoogle` には入れない
（`TaskLocalOnlyFieldsTests`）。

表示は、題名の後ろに薄く「↻」（`TaskItem.RepeatMark`）。右ペイン・月・週・日・一覧のタスクに出す。

### まだ合わせられていない項目

書き込みできる項目を全部洗い出して `google-field-gap.md` にまとめた。同期を始める
前に手を打たないと黙ってデータが失われるものが、予定側に6つ、タスク側に3つある。

保存できない間はボタンを止め、**理由を下に出す**。押せない理由が分からないのが一番困る。

### 入れやすさのための作り

1日に何度も触る画面なので、打鍵を減らすことを優先した。

- **時刻はゆるく読む。**「9」「930」「9:30」「０９：３０」のどれでも入る（`TimeInput`）。
  コロンと 0 埋めを毎回求めない
- **候補からも選べる。** 15分刻みの一覧を出す。終了側は
  「10:30（1時間30分）」と長さを添える。「何時まで」より「何時間か」で決めることが多い
- **上下キーとホイールで15分ずつ動く。** 一覧が開いているときは候補送りに譲る
- **開始を動かすと終了も同じ長さのまま付いてくる。** 終わりを打ち直させない
- **日付欄は中身ぶんの幅に留め、時刻と横に並べる。** 複数日のときは開始日と終了日を横に並べる
- **タスクの期限は「今日・明日・来週」から早入れできる。** 期限なしのタスクに使うと期限も付く

### 繰り返しの扱い

選択肢は「繰り返さない・毎日・毎週◯曜日・毎月◯日・毎年◯月◯日」の5つ。開始日に
合わせて文言が変わる。

取り込んだ予定が「隔週の月水金」のような選択肢で表せない指定を持っていることがある。
これは **`カスタム` として元の文字列をそのまま持ち続ける**。選択肢に無いからと消すと、
タイトルを直して保存し直すだけで繰り返しが失われる。

編集画面で触っていない項目（繰り返し、Google 側の ID と更新時刻、取り込み元）は
**そのまま引き継ぐ**。保存し直すたびにこれらが消えると、同期を始めたときに壊れる。

操作は右ペインから。行をダブルクリックで編集、指した行にだけ出る削除ボタン、
チェックで完了の切り替え。月ビューのマスは1回押しで選択、2回で予定の追加。
どれも `CalendarWorkspace` を通すので Ctrl＋Z で戻せる。

### 右ペインのタスクは「その日のぶん」ではない

未完了で期限のあるタスクを**期限の早い順にすべて**出し、完了済みは選択日に出すものだけ
添える。その日のぶんしか出さないと、今日やることは分かっても段取りが組めない。モックの
右ペインも 10/1 や 2027/3/31 期限のタスクを並べている。

見出しの「3 / 4」は**残っている数と全体**。片付いた数より、あと何件あるかのほうが知りたい。

### 完了したタスクは「完了した日」に出す

未完了は期限日、完了したタスクは**完了した日**（`CompletedAt` を端末のタイムゾーンに直した日付）
に出す。月・週・日・一覧・右ペインは同じ決まりで、決めているのは
`ScheduleQuery.PlaceTasks` の1か所（結果は `ScheduledTask`：日・見た目・添え書き）。

- 遅れて完了したもの（完了日 > 期限。数え方は実働日／暦日の設定どおり）は、完了日に
  「期限 9/7・4実働日遅れ」と添え、期限日にも**薄く**「9/11 完了」と残す
- 期限どおり・前倒しの完了は完了日にだけ出る（期限日には出ない）。前倒しは
  「3実働日 早く完了」を添える
- `CompletedAt` が無い完了タスク（古いデータ）は期限日、期限の無い完了タスクは完了日
- 薄い跡は右ペインの件数（「1 / 2」）に数えない
- 完了したチップはドラッグで動かせない（動かして変わるのは期限で、チップが出ているのは完了日のため）
- 完了日の検索は `tasks.completed_at` の索引（V9）を使う。時刻は epoch ミリ秒で日付は
  端末のタイムゾーン次第なので、SQL は前後1日広めに引き、日付の絞り込みは C# で行う

### WPF で踏んだ落とし穴

いずれもビルドは通るのに実行時だけ壊れるもの。

- **`StaticResource` は型変換を挟まない。** アイコンを `sys:String` で置いて
  `Path.Data` に渡すと `Geometry` にならず、読み込み時に落ちる。`PathGeometry` で持つ
- **`InputBinding` の中では `RelativeSource` で祖先をたどれない。** `InputBinding` は
  視覚ツリーに居ないため。マスや行のダブルクリックはコードビハインドで受けている
- **`RelayCommand` は `CommandManager` に乗っていない。** `RaiseCanExecuteChanged` を
  自分で呼ばないと、保存できるようになってもボタンが無効のまま戻らない
- **押された要素は Visual とは限らない。** `TextBlock` の中の `Run`（タスクの「↻」など）を
  押すと `e.OriginalSource` が `Run` になり、`VisualTreeHelper.GetParent` に渡すと例外で落ちる
  （v1.1.0）。親は `Views/TreeWalk.ParentOf` でたどる（`TreeWalkWiringTests` が見張る）
- **`Application.Shutdown()` は `Window.Closing` を出さない。** 更新のための終了は
  これを通るので、そこで保存していると何も残らない。ウィンドウの置き場所は動いた
  時点で控え、`Closed` で書き出している（`MainWindow.TrackPlacement`）
- **閉じたあとの `RestoreBounds` は当てにならない。** 窓のハンドルがもう無い。
  元に戻したときの大きさが要るなら、閉じる前に控えておく
- **窓を左の辺から広げると、描き直しが追い付くまで古い中身が左上に合わせて
  表示される。** 右に寄せた窓は左へ広がる形になるので、`Window.Width` を動かして
  開く演出を作ると（`SetWindowPos` で位置と大きさを1回にまとめても）、中身が
  壁から離れて左へ引きずられるように見える。左に寄せた窓は右へ広がるので、
  この問題は起きない。右のときだけ窓の大きさを一切変えず、`SetWindowRgn` で
  「見えている範囲」だけを壁側から広げるようにして避けた
  （`ShellController.SlideInRight`）。左右で作りを揃えようとすると同じ壊れ方に戻る

- **`Visibility="Collapsed"` でも `DataContext` のバインディングは起動時に評価される。**
  年・一覧のビューを `{Binding Year}` に結んでいたので、遅延にしたはずの
  `MainViewModel.Year`／`Agenda` が起動のたびに作られていた。重いビューは
  `YearForView`／`AgendaForView`（表示するまで null）に結ぶ
- **最初の HTTP 要求は、経路（プロキシ）の自動検出で呼んだスレッドのまま数秒止まる
  ことがある（会社の回線）。** 画面のスレッドから始めず、`Task.Run` の中で呼ぶ
  （更新の確認・実働日の配信の取得・Google の同期／接続／切断／追加認可・添付）。
  Google は `GoogleConnection` の入口が包んでいる。添付（`GoogleDriveAttachmentUploader`）は通信の
  呼び出しだけを包み、設定（画面側の DB）の読み書きは `ConfigureAwait(true)` で戻った画面のスレッドで行う。
  同期は専用の DB 接続（`App.xaml.cs` の `_syncConnection`）を使う。DPAPI（`DpapiTokenStore`）も同じく、
  ドメイン参加の PC では最初の呼び出しが遅いことがある
- **`HttpClient` は `Kado.Core.Net.KadoHttp` から作る。`new HttpClient()` と `HttpClientHandler` を
  他の場所に書かない。** 認証付きプロキシ（407）への対処（`DefaultProxyCredentials`）がハンドラの設定で、
  別の作り方をした場所だけ 407 で通らなくなる（`tests/Kado.App.Tests/NetworkWiringTests` が見張る）。
  通信の失敗は `NetworkLog` で `shell.log` に1行ずつ残し、画面の文言に例外の型名を出さない
  （`GoogleFailure`・`UpdateFailure`・`FeedFetchPolicy.Describe`）

- **WPF は、終了の問い合わせ（`WM_QUERYENDSESSION`）を取り消さないと、自分で
  `Application.Shutdown()` を呼ぶ。** 他のアプリがシャットダウンを取り消しても、Kado だけ終わっている。
  `SessionEnding` で `Cancel` すれば止まるが、Windows のシャットダウンまで妨げる。窓の外の独立した
  スレッド（`SessionEndWatcher`）が `WM_ENDSESSION` を見張り、取り消されたら立ち上げ直す。
  AppBar を外す後片付けは、問い合わせの時ではなく、終わるとき（`OnExit`、`WM_ENDSESSION` の
  wParam=TRUE）に行う
- **メッセージ専用の窓（`HWND_MESSAGE`）には、ブロードキャストが届かない。** Explorer の再起動で
  トレイのアイコンが消えたときに送られる `TaskbarCreated` を受けるには、見えないトップレベル窓
  （`WS_EX_TOOLWINDOW`）にする
- **WPF の `MessageBox` は、`MB_TOPMOST` を受け付けない**（未知のオプションは例外になる）。
  親の窓が無い起動時のメッセージが他の窓の裏に隠れるので、Win32 の `MessageBox` を直に呼ぶ
  （`FrontMessageBox`）。親にする見えない窓を作ると、それが最後の窓として閉じたときにアプリが終わる
- **`async void` から漏れた例外は、アプリごと終わらせる。** 通信・認可・ファイルを伴う入口
  （添付の追加）は、中で文言にして返し、`async void` のハンドラにも最後の `try/catch` を置く
- **`ConfigureAwait(false)` のあとで、画面用の SQLite 接続を触らない。** 接続は呼んだスレッドで
  使うもの。通信のあとに設定を読み書きするなら、`ConfigureAwait(true)` で戻ってから

- **コンバーターが `TryFindResource` で引いたブラシは、配色を当て直しても前のまま残る。**
  `DynamicResource` と違い、バインドの元の値が変わらない限り再評価されない。辞書から色を引く
  コンバーターには `IThemeSensitiveConverter` を付ける。`ThemeManager.Apply` が窓の木をたどって、
  その目印のバインドだけ `UpdateTarget` で結び直す（`tests/Kado.App.Tests` が付け忘れを見張る）。
  Style の `Setter` の中のバインドは対象外なので、そこでは使わない
- **ViewModel が作り直されても、画面（UserControl）の大きさが変わらなければ `SizeChanged` は来ない。**
  画面が測って ViewModel へ渡す値（週・日の時間軸の高さ、月のマスの数、年の幅）は、
  `DataContextChanged` でも測り直す。作りたての ViewModel は既定値のまま
- **.NET は `TimeZoneInfo.Local` と現在のカルチャの書式を、最初に読んだ値のまま持つ。**
  何日も動くので、タイムゾーンを変えられたら `ClockCaches.Refresh()`（画面のスレッドで）で捨てる。
  作った時点のゾーンを欄に握らず、毎回 `TimeZoneInfo.Local` を見る（`ScheduleQuery`）。
  `SystemEvents` の通知は画面のスレッドには来ない
- **同期は別の接続で書くので、画面は書かれたことを自分では知らない。** 中止・失敗で途中から抜けても、
  書いた可能性があれば読み直す（`IGoogleSync.MayHaveWrittenBeforeInterruption`、`SyncReport.MayHaveWritten`）。
  分からないときは読み直す側に倒す

- **`shell.log` への書き込みは、呼んだスレッドでは行列に積むだけ。** 別のスレッド（`BufferedLogWriter`）が
  まとめて書く。ウイルス対策ソフトのファイル検査がある PC で、画面のスレッドが1行ごとに止まらないため。
  そのかわり**書き込みは遅れる**ので、終わるとき・異常終了のときは `ShellDiagnosticsLog.Flush()`
  （`App.OnExit`・`ReportFatal`・シャットダウンの確定）。世代は `shell.log`・`.1`・`.2` の3つ、1つ1MBまで。
  窓の移動通知や演出のコマごとの行のような高頻度の行は `WriteThrottled`（1秒に1行、あとは
  「同種の行を n 回省略。これが最後の値」の1行）。**起動の計時・更新・Google・配信の行には使わない**
- **仮想化は、`ScrollViewer` が `ItemsControl` のテンプレートの中で `ItemsPresenter` を直に包んでいるときだけ
  効く。** 外に `ScrollViewer` があると、全行の入れ物を作ってしまう（一覧ビュー）。仮想化すると、見えていない
  行の入れ物は無い（`ContainerFromItem` が null）ので、`VirtualizingPanel.BringIndexIntoViewPublic` で
  作らせてから測る。`Rows` を丸ごと入れ替えるとスクロール位置が先頭へ戻るので、見ていた日へ戻している
  （`AgendaView` の目印）
- **`Visibility="Collapsed"` の側もバインドとコンバーターは評価される。** 月のマスはふつうの形と詰めた形を
  別の `DataTemplate` にして、`CellsHost` の Style が `IsCompact` で `ItemTemplate` を差し替える。
  マスのテンプレートの中に `IsCompact` を結ばない（マスごとに RelativeSource のトリガーが増える）
- **コンバーターは、色の文字列から凍結したブラシを作って使い回す（`BrushCache`）。配色の辞書からの引き当ては
  `ThemeResources.Find` で、配色を当て直すまで同じ結果を使い回す。** `ThemeManager.Apply` が辞書を入れ替えた
  直後に `ThemeResources.Invalidate()` を呼び、そのあとでバインドを結び直す。この順を変えると前の配色が残る
- **幅をつまんでいるあいだは、`DockWidthChanged`（動かすたびに来る）で保存しない。** 保存は
  `DockWidthCommitted`（つまんでいないときの変更はその場で、つまんでいたなら離したときに1回）で受ける
- **`StaticResource` は、定義より前には書けない。** 辞書の中で、後ろで定義するスタイルを `BasedOn` や
  `Style=` で引くと、ビルドは通るのに起動時（辞書の読み込み）で落ちる。後ろのものは `DynamicResource` で引くか、
  定義より後ろに置く。暗黙の `MenuItem`／`Separator` スタイルを `BasedOn="{StaticResource {x:Type MenuItem}}"` で
  引き継ぐスタイルも、暗黙スタイルより後ろに置く（`Themes/Controls.xaml` の右クリックメニューは末尾近くにある）。
  `tests/Kado.App.Tests/ContextMenuOpenItemsTests` が、`Controls.xaml` の前方参照と `BasedOn` の抜けを検査する
- **`MenuItem` に `Style` を明示すると、暗黙のスタイルは当たらなくなる。** 枠や色が Windows 既定に戻る。
  明示するときは `BasedOn` を付ける（入れ子の `ItemContainerStyle` も同じ）

起動が遅いときは `shell.log` の `startup-timing`（印ごとの累計と区間）と
`startup-slow`（起動中に100msを超えた処理）を見る。仕掛けは
`Kado.Presentation.Infrastructure.StartupTrace`。

`tests/Kado.App.Tests` が、`StaticResource` の型変換、`StaticResource` の前方参照、`MenuItem` の `BasedOn` の抜けを
静的に検査する。`InputBinding` と `RelayCommand` の2つは検査できていないので、同じ書き方をしないよう上に残した。

## シェル統合（Phase 5）

要件書 2章の最重要要件。実装は `src/Kado.App/Shell/`。

### 3つの出しかた

| 出しかた | 普段 | ワークエリア |
|---|---|---|
| ウィンドウ | ふつうの窓 | 削らない |
| スライド | **画面から消えている** | 削らない |
| 固定（ピン） | 画面端に出たまま | **削る** |

スライドは普段隠れていて、画面の端に 0.3 秒ほどマウスを留めると出てくる。帯の幅は
8px。要件書は3〜5px だが、実機で「端に当てても出てこない」となった。高 DPI では
数ピクセルが目視でほとんど無いに等しい。見張る画面は張るときに1回だけ決める。毎回
カーソルからモニタを引き直していたが、呼び出しが1つ増えるぶん失敗する余地があり、
失敗すると黙って出てこなくなる。他の
ウィンドウへ移ると引っ込む（自分が出した編集画面へ移ったときは引っ込めない。
書いている最中に本体が消えると、書き終わって戻る先が無くなる）。

出たところでピンを押すと、そのまま固定して画面を分割する。

**固定中は枠が消えるので、戻り口を複数用意してある。** ツールバーのピン、
ツールバーの▥（出しかたとパネルの選び方）、トレイのメニュー、Ctrl＋Alt＋P。
1か所しかないと、そこが隠れたときに詰む（実際にツールバーの中身がはみ出して
ピンが押せなくなり、解除できなくなった）。

### 2段構えにしてある理由

Windows では**自動非表示の AppBar はワークエリアを削らない**。削らないと、他の
ウィンドウを最大化したときに重なってしまう。出入りのたびに登録・解除すれば理屈の
上では削れるが、そのたびに全ウィンドウがリサイズされて実用にならない。

だから「ホバーで呼び出す（オーバーレイ）」と「ピンを押して画面を分割する（ドック）」
を別の状態にしてある。ピンを押したときだけ `ABM_NEW` する。

### 削ったまま落とさないための3点（要件書 2.3）

`ABM_REMOVE` を呼ばずにプロセスが落ちると、**ワークエリアが削られたまま残り、
ユーザーのデスクトップが壊れる**。最大化したウィンドウが画面いっぱいにならなくなり、
アプリを消しても直らない。

1. `DispatcherUnhandledException`・`AppDomain.UnhandledException`・`SessionEnding`
   のすべてで外す（`App.ReleaseShell`。何度呼んでも安全にしてある）
2. ミューテックスで二重起動を防ぐ（`SingleInstance`。多重登録を防ぐ）
3. 削る前に `settings` へ印を書き、戻したら消す。起動時に印が残っていれば異常終了
   なので、`SPI_SETWORKAREA` で全モニタを元に戻す（`WorkAreaGuard`）

印を書く順序が肝。**削る前に書き、戻したあとに消す。** 逆にすると、その隙に落ちた
ときに記録が残らない。

### 要件書と変えたところ

- **ホットゾーンに透明ウィンドウを置かない。** 要件書は `WS_EX_TRANSPARENT` の帯を
  常駐させて `WM_MOUSEMOVE` を拾う案だが、この拡張スタイルを立てた窓はヒットテスト
  から外れるので、そもそもマウスのメッセージが来ない。立てなければ来るが、今度は
  画面端にあるウィンドウの閉じるボタンやスクロールバーが押せなくなる。低レベルの
  マウスフックは全入力を見る形になり、ウイルス対策ソフトに止められることがある。
  カーソルの座標を 100ms ごとに見るだけにした（`EdgeHotZone`）。窓を置かないので
  他の操作を一切邪魔しない。誤爆防止の滞留（250ms）は要件どおり
- **トレイは `Shell_NotifyIcon` を直に呼ぶ。** WinForms の `NotifyIcon` を借りると
  `UseWindowsForms` が要り、WPF と同じ名前の型が大量に入って衝突する（実際に
  ぶつかった）。受け皿として `HWND_MESSAGE` の窓を1つだけ持つ
- **アイコンは exe から `ExtractIconEx` で引く。** 配布物は単一ファイルなので、
  隣に .ico を置いておけない

### 幅の交渉

`ABM_QUERYPOS` が返す矩形は、タスクバーや他社製 AppBar との調整が済んだ値。
**希望した値のまま `ABM_SETPOS` に渡してはいけない。** 返ってきた矩形から、改めて
自分の幅ぶんを切り出す。

ワークエリアを変えると他プロセスのウィンドウまで並び替わるので、ドラッグ中は
呼ばない。手が 250ms 止まってから交渉し直す。ただし**窓の幅だけは即座に動かす**。
交渉が済むまで何も動かないと、掴んで引いてもびくともしないように見える。

### P/Invoke で文字セットを省くと、遠くで症状が出る

`GetMonitorInfo` の宣言に `CharSet` を書かなかったせいで、**スライドが画面端で
出てこない・ピン留めすると高さが足りない・他のウィンドウを最大化すると重なる**の
3つが同時に起きていた。

`DllImport` は既定で ANSI 版（`GetMonitorInfoA`）に結び付く。一方 `MONITORINFOEX` は
`CharSet.Unicode` で並べてあるので名前の欄が 64 バイトになり、`cbSize` が ANSI 版の
想定と合わない。**結果として、いつ呼んでも `false` が返る。**

これを「引けなかったので 0 の矩形」として素通りさせていたため、画面端の帯は
「幅0の画面」を見張ることになって二度と反応せず、AppBar は高さ0の枠を交渉しに
いっていた。どちらも「押しても何も起きない」としか見えず、原因から遠いところで
悩むことになる。

対処は2つ。宣言に `EntryPoint = "GetMonitorInfoW"` と `CharSet.Unicode` を書くこと
（`NativeMethods`）。そして、引けなかったときに 0 を返さずプライマリ画面で代用する
こと（`Screens`）。**Win32 の失敗を 0 のまま流さない。**

### 狭いときに畳むもの

落とす順は使う人に決めてもらった。ツールバーは実働・残りのバッジ（1000px）
→ 同期の状態（880px）→ 検索を虫めがねに畳む（820px）→ ビュー切り替え
（700px）。年月の見出し・「◀ ▶」・今日・≡ は残し、戻り口になるピン・▥・
設定は常に置く。

パネルは左 → 右 の順。**ただし畳むのは、ほかに出ているものがあるときだけ。**
出ているのが1つなら、それが何であれ残す。右ペインだけを出して使っているのに、
狭めたらそれが消えて中央のカレンダーが出てきた、という形で実機から返ってきた。
細い帯では右ペイン（予定・タスク）を主に使う。

### スリムパネル

4つ目のパネル。ひと月の並びと、選んだ日の予定・タスクだけを細く置く。

**幅では切り替えない。** 狭いときに別の形へ化ける作りにしていたが、同じ操作を
探し直すことになる。出すかどうかは、ほかのパネルと同じく手で選ぶ。パネルの
自動の畳み込みもやめた。出しておきたくて出しているものが、幅の都合で消えるのは
筋が悪い。入りきらないぶんは切れるだけにする。

- 月だけを出す。週や日は時間軸が要るぶん、この幅では読めない
- 自前の月暦（`MainViewModel.SlimMonth`）を持つ。中央が何を出していても、
  こちらはひと月の並びを見せ続ける
- マスには予定の名前を出さない。日付と、予定が入っていることを示す色の帯だけ。
  実働日カレンダーの印は日付の上、それ以外は下（`MonthViewModel.IsCompact`）
- マスは正方形が下限。高さに余裕があれば伸びる
- **日付の上は、いつも帯1本ぶんの高さを取る。** これでどの日も日付の高さが揃う。
  2本ぶん取ると、そのぶん下の予定に回せる行が減る。今日のマスは枠のぶんだけ
  内側の余白を減らし、ほかの日と同じ位置に置く
- マスに操作の説明は出さない。小さいマスに載せるたびに3行の吹き出しが開いて、
  隣の日が隠れる
- 予定とタスクは縦に続けて置く。タブにすると、片方を見ているあいだもう片方が
  見えない

### 残りの幅を受け取るのは1つだけ

中央 → 右 → 左 → スリム の順で決める（`MainWindow.ApplyPanes`）。どれかが
「*」でないと、窓を広げたぶんが誰にも行き渡らず黒いまま余る。パネルごとに
別々の条件で決めていたら、スリムパネルだけを出したときに受け取り手が
いなくなっていた。受け取る列は上限も外す。付けたままだと、そこで止まって
先が余る。

### 出しているパネルと幅は、居かたごとに覚える

ウィンドウのときと、画面端に寄せている（スライド・固定）ときとで別に控える。
広いウィンドウでは3つとも出し、細い帯では予定だけ、という使い分けがふつうなので、
行き来のたびに直すのは手間になる。幅も同じで、スライド・固定・ウィンドウの
3つを別に持つ。

いちばん細くできる幅は設定で決められる（160〜640px）。帯としてどこまで詰めたいかは
使う人による。**窓の下限（`Window.MinWidth`）と帯の幅の下限（`ShellViewModel.MinWidth`）の
両方に効かせる。** 片方だけ下げても、もう片方が押し戻すのでそこまで細くならない。

組を入れ替えている最中は「3つとも畳んだら1つ戻す」を止める。閉じてから開くので
途中で空の状態を通り、そこで中央を戻すと、読み込んだ組に余計なパネルが混ざる。

### 大きさが変わるたびに組み直さない

**週と日が軽くて、月・年・一覧が重かった理由。** 前の3つは大きさに合わせて
組み直すものを持たないが、月はマスに入る件数を、年は 372 個のマスの幅を、
それぞれ測って決めている。`SizeChanged` は1ドラッグで何十回も来るので、掴んだ
瞬間に固まっていた。

`Settle` に渡して、手が止まってから1回だけ走らせる。年のマス幅は 1px 単位に
丸める。端数のままだと、動かすたびに 372 個の幅がすべて引き直される。

### スライドの出入り

**出るのは帯に留まったとき、引っ込むのはカーソルが外れたとき。** 出す判定は
250ms、引っ込める判定は 400ms と長めに取ってある。端を掠めただけで消えると、
押そうとしたボタンが逃げる。引っ込め方は設定で切れる（既定は引っ込める）。

横に滑らせる。出るとき 220ms の減速（QuinticEase の EaseOut）、引っ込むとき
160ms の加速（QuadraticEase の EaseIn）。用が済んだものを見送らない。

**アニメーションを掛けたら、終わったところで外すこと。** `BeginAnimation` で
動かしたプロパティは、そのあと値を握り続ける。外さずに `Left` へ代入しても
効かず、位置が動かない理由が分からなくなる。

**幅を変えたら、見張る矩形も合わせること。** 出したときの矩形のまま見張って
いると、掴んで広げた先にカーソルを置いた時点で「外れた」ことになって引っ込む。
狭める向きに引くと、つまんでいる手そのものが窓の外へ出るので、つまんでいる
あいだは引っ込めない（`ShellViewModel.IsResizing`）。どちらも「スライドでは
幅を変えられない」という形で出る。

**見張る矩形は「落ち着いたあとの居場所」で取ること。** 滑り込ませる前の
`Left` は画面の外を指しているので、そのまま渡すと画面外の矩形を見張ることに
なり、カーソルがどこにあっても「外れている」と判定されて出たそばから引っ込む。

### 画面の構成が前日と違うとき、変わったとき

ノート PC を持ち出す・戻すと、前日と画面の構成がまるごと違う（実機：前日は物理 2880x1824・
200% の単独、当日は 1920x1080 の主画面＋左に 1024x1280）。ログオン直後は、起動のあとも
モニタの数・位置・倍率が数秒〜数十秒かけて変わる。控えてあった位置をそのまま信じると、
**窓が全部の画面の外に置かれる・存在しない画面の端を見張り続ける**ので、出てこない
ように見える。

- **起動時（`ShellController.Restore`）**：窓の矩形と今の画面の一覧から置き場所を決め直す。
  普通の窓は、どの画面にも手が届くほど乗っていなければ主画面へ収める。スライド・ピン留めは、
  窓が乗っている画面の端へ、どの画面にも乗っていなければ主画面の同じ端へ。**乗っていれば
  何も変えない。** 判断は `ShellGeometry`（`RestoreWindow`・`DecideEdge`）に寄せてあり、
  実機の数値で `ScreenLayoutTests` が確かめている
- **起動のあと（`SystemEvents.DisplaySettingsChanged`・`Window.DpiChanged`）**：続けて来るので
  700ms 待ち合わせてから、今の居かたのまま決め直す。スライドは窓と帯の見張りを今の画面で
  張り直す。ウィンドウは主画面へ収める。ピン留めは `AppBarHost` が `WM_DISPLAYCHANGE` で
  動くので、落ち着いてから交渉し直すだけ（同じ矩形なら何もしない）。開く演出・引っ込め・
  幅つまみ・ピンの交渉の最中は、済むまで待つ。起動の直後にも1回、同じ確認をする
- **スライドが出たままになる経路を1つ塞いだ。** 窓が隠れている（トレイへ閉じた）のに
  「外れるのを見張る」状態のまま残ると、帯が二度と反応しなかった。隠れていると分かった
  時点で帯の見張りへ戻す

`shell.log` で読むところ：

- `startup-restore mode=… saved=… screens=… 置き直し=はい|いいえ 理由=…` が、起動時の判断
- `startup-restore 結果 …` が、置いたあとの窓の矩形（`GetWindowRect`）と見えているか
- `display-change cause=… 構成変化=あり|なし …` が、起動後の決め直し
- `SlideOut 見送り 理由=…` が、引っ込めるのを見送った理由（理由が変わったときだけ出る）。
  起動のあとに `OffScreenLeft` が出ないときは、ここが出ているかで切り分ける
- `startup virtualScreen=(left=…,width=…)` は**左端と幅**。`(-1024,2944)` は「左端 -1024、
  幅 2944（＝1024＋1920）」で、右端が 2944 という意味ではない（以前は見出しが無く、取り違えた）

実機でしか確かめられない：倍率の違う画面へ移したときに Windows が切り替える倍率（
`OverlayBounds … 置き直す` の行が出るか）、ログオン直後に本当に何回・どんな順で構成が
変わるか。

### 窓を細くできるようにする

**下限は `Window.MinWidth` ただ一つで決まる。** `MainWindow.xaml` に
`MinWidth="880"` が残っていて、そこから縮まなかった。画面で測ると 866px に
見えるのは、Windows 11 の**見えないリサイズ枠**が左右に 7px ずつあるため。
`880 − 14 = 866`。この 14px のずれのせいで、しばらく別のところを疑っていた。

`SizeToContent` を使わない `Window` は、**中身が要る大きさを Windows に伝えない。**
「ツールバーの積み上げが下限を押し上げている」という見立ては間違いだった。
`WM_GETMINMAXINFO` を横取りする手も要らない。WPF の `Window` 自身が
`MinWidth` をそこに書いて返すので、値を直せば済む。

この下限は、幅で畳む仕組みごと殺していた。`ActualWidth` は `MinWidth` を
下回らない（HWND が細くなっても、中身は `MinWidth` で測られて右が切れるだけ）
ので、880px を境にした出し分けが一度も発火しなかった。ピン留めで頼んだ幅
（既定 352px）も 880 に引き上げられ、譲ってもらった幅より窓が広くなって
他のウィンドウと重なっていた。**ひとつの値が、症状を4つ作っていた。**

詰め方に渡す幅は `Window.ActualWidth` ではなく、中身の根元（`Root`）の
`ActualWidth` にしてある。見えない枠を含まず、`MinWidth` でも下げ止まらない。

### まだ手を付けていないところ

- **日付欄のポップアップは WPF 既定の暦のまま。** 外側の枠と高さは周りに揃えたが、
  開いたあとの暦は既定の見た目。ここを作り替えるのは別の仕事として残してある
- **Phase 5 は実機で一度も確かめていない。** WPF も Win32 も Linux では走らせ
  られないので、確かめられたのはコンパイルが通ることと、居かたの切り替え・
  居場所の出し入れ・安全装置の印だけ（`ShellModeTests`）。AppBar が本当に
  ワークエリアを削るか、他のウィンドウを最大化しても重ならないかは、Windows で
  見るまで分からない
- **トーストは自前のウィンドウのまま。** 非 MSIX 配布で OS のトーストを出すには
  AUMID の登録と COM アクティベーターが要る（要件書 7.5）。いまは画面右下に
  自前の窓を出している。トレイのバルーン（`TrayIcon.ShowBalloon`）も口だけは
  用意してあるが、まだ繋いでいない
- **繰り返しの例外回をこちらから作る道筋が無い。** 画面で「この回だけ」を変える
  操作はまだ無い

## 取り込みの呼び出し口

ツールバーの ⚙ から開くメニューに置いた。

| 取り込むもの | 形式 | 重ね方 |
|---|---|---|
| 配布の実働日ファイル | Excel | **期間単位で置き換える。** 古いファイルを誤って読み込んでも、その期間の外は消えない（要件書 4.1） |
| 旧 inaCalendar のバックアップ | JSON | 同じ識別子の予定とタスクを上書き。実働日は既存と併合する |

どちらも **Undo には積まない**。まとめて書き込むので、1手で戻せる単位にならない。
旧データの取り込みは元に戻せないので、先に断りを入れてから選ばせる。

読めないファイルを選んでも落とさない。何が起きたかを結果の窓に出して続ける。

## 同期の作り

### 回す順序

**削除を伝える → 取り込む → 送る**。削除を先に伝えないと、消したものが取り込みで
復活する。取り込みを送信より先にするのは、衝突したとき相手を採る方針に合わせるため。

### 衝突したとき

どちらも変わっていたら**相手（Google）を採る**。予定は複数の端末や同僚から書き換わる
もので、そちらが正であることが多い。こちらの端末で開いたまま放置した内容が、
他の人の変更を押し戻すほうが困る。

ただし**消したほうが勝つ**。消したのに戻ってくるのは、変更が消えるより分かりにくい。

**相手が変わっていなければ触らない。** ここを入れないと、差分の印が古くなって全件が
降ってきたとき、まだ送れていないこちらの変更を押し潰す。控えた生データ（`google_raw`）
と見比べて判定する。

### 差分の取り方が Calendar と Tasks で違う

Calendar は `syncToken`。**410 が返ったら印を捨てて全部取り直す**（要件書 6.3）。
Google は古い印を無期限には覚えていない。

Tasks に `syncToken` は無い。前回いつ取りに行ったかを覚えて `updatedMin` に渡す。
時計のずれで取りこぼすより同じものを二度読むほうが安いので、5分前から取り直す。
`showDeleted` と `showHidden` を立てないと、消えたものと完了したものが降ってこない。

### 消えたことの伝わり方も違う

Calendar は `status=cancelled`、Tasks は `deleted: true`。Tasks の `hidden`
（完了して一覧から隠れただけ）は別物なので混ぜない。混ぜると完了しただけのタスクが消える。

相手が消したときは `tombstones` に残さない。相手はもう知っているので、残すと次の同期で
消しに行ってしまう。**こちらで消したときだけ残す**。伝え終わったら消す。残し続けると、
同じ ID が再利用されたときに新しいほうまで消してしまう。元に戻したときも記録を消す。

### 書き戻しは patch

`update`（PUT）だと本文に無い項目が消える。ゲスト・通知・会議室など、このアプリに
欄が無いものまで巻き添えになる。とくに**配列は丸ごと置き換わる**ので、`attendees` を
うっかり空で送るとゲストが全員消える。送らなければ無傷で残る。

送ったあとは応答をそのまま控える。控えないと毎回「変わった」と判定して送り続け、
相手側でも更新時刻が動いて「変わった」と見えてしまう。

### 日付のずれ（2か所とも往復テストで押さえてある）

**終日予定の終了日は Google では翌日を指す（排他）。** 9月24日だけの終日予定は
`end.date=2026-09-25` で届く。こちらは最終日を含むので、読むときは1日引き、書くときは
1日足す。取り違えると同期のたびに予定が1日ずつ伸びていく。

**タスクの期限は UTC の 00:00 として届く。** 日本時間で解釈すると9時間ぶん前の日付に
なって1日ずれる。UTC のまま日付だけを取る。

### 重複を作らない

送ったあと応答を受け取る前に落ちると、次の同期で同じものが降ってくる。結び付いて
いない同じ内容のもの（題・日付・開始時刻、タスクは題・期限）を探して引き受ける。
**探す範囲は、いま取り込んでいるカレンダー／リストに対応するこちらのカレンダー／リストの
中だけ。** 広げると、このアプリの中だけのカレンダーの予定や、別のカレンダーに送る
つもりの未送信の予定が、たまたま同じというだけで吸い込まれて上書きされる。

**書き換えようとして 404 が返っても、結びを外して作り直さない。** 向こうでは別の
カレンダーへ移っただけのことがあり、外して次の同期で insert すると、ゲスト・会議 URL・
添付の無い写しが二重にできる。予定・タスクに「Google 上で見つからない」印
（`events.google_missing` / `tasks.google_missing`、V10）を付けて、以後は送らない。
同期の警告に題を出し、編集画面にもその旨と「Google に新しく作り直す」ボタンを出す。
押したときだけ結びを外して新規として送る。印を付けたものが、あとの取り込みで見つかれば
（別のカレンダーにいた、など）印を外して結び直す。

### 同期が書き換えたものを、画面や Undo が古い値で戻さない

予定・タスクの項目は2つに分かれる。使う人が編集する**中身**（題・日時・繰り返し・場所・
メモ・通知・色・入れ先の希望・完了状態など）と、同期だけが書き換える**結び付き**
（Google の ID・実際にいる入れ先・控えた生データ・更新時刻・状態・親子関係と並び順・
「見つからない」印）。**書き込むときは、中身は編集の前後（画面）から、結び付きは書き込む
時点の最新の行から採る**（`Editing/SyncLinks`）。

- 元に戻す・やり直し（`Editing/Edits.cs`）と編集画面の保存は、どちらもこの形で書く。
  同期のあとで戻すと、戻した内容が「同期済み」に見えて送られない、移動を戻すと実際の
  入れ先まで古い値に戻って次の編集が 404 → 二重になる、といったことが起きていた
- 追加を元に戻すとき、Google と結び付いていれば削除の記録を残す（Google からも消す）。
  やり直しは Google の ID を持たない新しい予定として入れる
- 削除を元に戻すとき、記録がまだ残っていれば消して元通りに、**もう伝え終えて Google から
  消えているなら**、Google の ID を持たない新しい予定として作り直す
- 削除の記録の持ち主は、Google で**実際にいる**カレンダー（`GoogleCalendarId`、無ければ
  `CalendarId`）。入れ先の希望だけ変えて move を送る前に削除すると、希望先へ削除を
  投げて 404 → 記録を捨て、元の場所に Google の予定が残る
- 編集画面を開いている間も裏の同期は走る。保存の前に、開いた時点と今の Google 側の姿
  （更新時刻・控えた生データ）を比べ（`Editing/EditConflict`）、変わっていたら
  「上書きしますか」と尋ねる（いいえなら編集画面に戻る）。行が無くなっていたら保存しない

### 消されたとき、未送信の編集を黙って捨てない

Google 側の削除（`cancelled` / `deleted`）でこちらの行を消すとき、まだ送っていない編集
（内容の差・添付の指定）があれば、警告に題を出す。

こちらで入れ先を変えて move を出した直後に切れると、Google では移っているのに手元は元の
カレンダーにいるつもりで、元からの `cancelled` を受け取る。消す前に、移し先（入れ先の
希望）で `events.get`（タスクは `tasks.get`）をして、あれば「移動は済んでいた」として
入れ先だけ直し、消さない。

### 一覧から外れたカレンダー

カレンダー一覧は `showHidden=true` で取る。付けないと、Google の一覧から隠しただけのものが
返らず、「消えた」と取り違えて予定ごと捨てる。本当に消えた（購読解除・削除）ときも、まだ
送っていない予定・編集・削除の記録があれば、捨てずに「Google から外れた」印
（`calendars.google_detached`）を付けて同期だけ止め、警告を出す。使う人が中身を確かめて
消し、送っていないものが無くなれば、次の同期でふつうに外れる。再び一覧に現れたとき、
隠していたものを表示に戻したときは、差分の印（syncToken）を捨てて全件取り直す。

### 表せない繰り返し

RDATE など、こちらの繰り返しの形（`Recurrence`）に収まらない指定は、生データだけ控えて
`Recurrence` を空にしてある。向こうでは繰り返しの予定なので、ドラッグで開始日を動かすと
系列の開始がずれる。`EventMapper.HoldsUnrepresentableRecurrence` が真の予定は、
繰り返しの予定と同じに扱う（ドラッグで動かせない）。編集画面では日時と繰り返しの欄を
動かせなくする（題・場所・メモなどは直せる）。

### 使う人が変えていないものは、Google が持っているままにする

送るのは「使う人がその項目を変えたとき」だけ。変えていないのに送ると、向こうで変えた値や
他の道具が付けた値を黙って書き換える。

- **カレンダーの色・呼び名**：Web で変えたのに、手元が旧いままだと「こちらで変えた」と取り違えて
  旧い値を送り返していた。**最後に Google から受け取った姿（`calendars.google_raw`）と手元を
  比べ**、手元が変わっているときだけ送る。Google 側が変わっていれば Google に従う
- **時差（`start.timeZone` / `end.timeZone`）**：America/New_York などで作られた予定を、題だけ
  直して送ると、この PC の時差に書き換わり、繰り返しの回の時刻が夏時間でずれていた。受け取った
  姿に時差があれば、それを保つ。日時を変えたときも、**手元の時刻を元の時差に直して**送る。
  新規と、元に時差が無いものだけ、この PC の地域を使う
- **タスクの完了日時**：`status` だけ送ると Google が「いま」を完了日時に入れ、手元の完了日時
  （「N実働日 遅れて完了」の根拠）まで置き換わっていた。完了にしたときは手元の完了日時を
  `completed` として送る。未完了に戻したときは `completed: null` と `hidden: false`
  （完了で隠れた印を外す）を送る。完了・未完了を変えていなければ、どちらも送らない
- **`source`**：予定の題を直して保存すると、`source.title` が予定の題に書き換わっていた
  （編集画面が受け取った `source.title` を落としていた）。引き継ぐようにし、`source` は
  **URL を変えたときだけ**送る。URL を変えたときも、受け取った `source.title` を保つ。
  新規だけ、予定の題を `source.title` にする
- **除外日（EXDATE）**：例外回（動かした回・中止した回）のために、取り込みは親の `Recurrence` へ
  `EXDATE=` を足す。親を送った応答を取り込むと、Google の行にはそれが無いので消え、動かした回が
  元の日にも出ていた。**前に Google から受け取った行に無かった除外日だけ**引き継ぐ（Google が
  外した除外日は残さない）。編集画面も、繰り返しの種類は除外日を除いた RRULE で判定し
  （毎週のままなら曜日の追従が効く）、保存するときに除外日を引き継ぐ
- **時刻つきの EXDATE**：系列の開始時刻を変えて送るとき、元の `EXDATE;TZID=…:20261005T090000`
  がそのままでは新しい回と合わず、除外が外れて中止した回が復活する。**日付はそのまま、時刻だけ**
  を新しい開始時刻（その EXDATE の時差で見た時刻）に書き直す。TZID と書式は保つ。終日の
  EXDATE は触らない。開始時刻を変えないときは一字一句そのまま

### Google では移せないもの

`events.move` は、繰り返しの1回だけの回、**他人が主催する予定**（`organizer.self` が false。
`guestsCanModify` が立っていても、移せるのは主催者だけ）、`eventType` が default 以外
（focusTime・outOfOffice・workingLocation・fromGmail・birthday）を受け付けない。
`EventMapper.MoveBlockReason` が見分け、編集画面はカレンダー欄を変えさせず理由を出す。
タスクは、サブタスクと、サブタスクを持つ親（手元で `ParentId` から参照されているもの）の
リスト移動を止める（`TaskMapper.MoveBlockReason`）。

**移せないものを送ってしまったときも、同期を止めない。** move が断られたら（または、上の
移せないものに移す指示が残っていたら）、警告にして入れ先の希望を元に戻し、一緒に直した内容は
元のカレンダー／リストへ PATCH で送る。以前は move の失敗で内容の送信まで止まり、同期のたびに
同じ失敗を繰り返していた。

### 全件を取り直したとき、Google で消えたものを拾う

差分（予定は `syncToken`、タスクは `updatedMin`）では、消えたものが `cancelled` /
`deleted` で降ってくる。ところが **410（`syncToken` の期限切れ）や繋ぎ直しで全件を取り直す**と、
予定は `showDeleted=false` で取るため、その間に Google で消えた予定は降ってこず、手元に残る。
タスクも、時間が経つと `deleted: true` で降ってこなくなる。

全件を最後まで取れたときだけ、**一覧に無い・手元にだけある Google と結び付いたもの**を見つける。
未送信の変更（内容・添付・別のカレンダーへ移す指示）が無ければ手元から消す（Google には何も送らない）。
あれば消さず、「Google 上で見つからない」印を付けて警告する。**期間を切って取っているとき**
（`IEventGateway.ListFrom`＝`timeMin`）は、その期間より前の予定は一覧に載らないだけなので消さない。
繰り返しは、期間に届くとはっきり言えるもの（終わりが無い・終了日が期間以降）だけを見る。

### 削除の送信が断られても、同期を止めない

削除の送信で 404 / 410 以外の 4xx（400 など）が返っても、そのカレンダー／リストの同期を丸ごと
止めない。その削除だけを警告にして**記録を残し**（次回やり直す）、ほかの送信・取り込みは続ける。
403 で**権限が無いと分かるもの**（読み取り専用になった、主催者でない、など。呼びすぎ・容量の
403 は含めない）は、何度送っても通らないので記録を捨てて警告する（`GoogleApiException.IsPermissionDenied`）。

### 同期の警告

右上の表示には最初の1件と残りの件数（「…ほか2件」）を出し、全文はツールチップと
⚙の「接続の状態」の下の一覧で読める。**警告は、使う人が読んだことにするまで消えない**
（次の同期が無事でも残る。裏で15分ごとに回るので、気づく前に消えると何が伝わらなかったのか
分からない）。読んだことにするのは、⚙の「確認した」か、右上の表示の右クリック。
同じ文は重ねず、100件を超えたら古いものから落とす。

警告とは別に、同期で起きた**知らせ**（`SyncReport.Notes`。繰り返しの次の回を作った、など）がある。困りごとではないので
警告に入れず、同期の表示を「警告」にしない。下のステータスで一度だけ伝える。

### 送れないカレンダー（読み取り専用・Google から外れた）

**読み取り専用**と「**Google から外れた**」（`google_detached`）カレンダーには、予定を入れても
送れず、手元にだけ溜まる。新しい予定の入れ先の既定・1行入力・編集画面の候補・予定の移し先から
外す（`SourceListItemViewModel.CanReceive`）。設定がそこを指していても、先頭がそれでも入れない。

すでに入ってしまった**送れない予定は、手元だけで削除できる**（Google には何も送らない。削除の
記録を残さない）。対象は、「Google から外れた」カレンダーの中身すべてと、読み取り専用の
カレンダーのうち**一度も Google に送っていない**予定。Google から受け取った予定は、手元だけ消しても
Google には残るので、これまでどおり止める。

**こうした予定を開くと、直せる編集画面ではなく読み取り専用の画面**（右クリックの「詳細を見る」。ダブルクリックも同じ）が
開く。上に理由が出て、欄は触れず、保存も削除もできない（以前は理由を下のステータスに出して、何も開かなかった）。
Google 側で変えられない予定（メールから作られた予約・誕生日・勤務場所・他人が主催する予定）も同じ扱い
（`MainViewModel.EditBlockReason`）。

「Google から外れた」カレンダーは、左パネルの行に「外れた」の印を出し、説明をツールチップに出す。
中の予定は見られるが、変えられない（同期が止まっているので）。行の右クリックに「削除」を出し、
確認のうえ、**中の予定ごと**手元から消せる（確かめてから消す、という警告の導線）。通常の削除
（中身を別のカレンダーへ移す）とは違う。

**タスクリストも同じ**（`task_lists.google_detached`、V11）。Google の一覧から消えたとき、
送っていないタスク・編集・削除の記録が無ければ、一覧から外す（中のタスクごと）。あれば
捨てずに残して印を付け、同期を止めて警告する。再び一覧に現れたら、`updatedMin` を捨てて
全件を取り直す。以前は何もせず、消えたリストを毎回読みに行って、同期のたびに警告が出ていた。

### 重複の整理

同じカレンダー・日・時刻・題の予定を1つにまとめるとき、**ゲスト・会議 URL（`conferenceData` /
`hangoutLink`）・添付を持つもの、他人が主催するものは必ず残す**（Google 側にしか無い情報で、
消すと取り戻せない）。2件以上が持っているときは、どれも消さない。

### 画面からの動かし方

⚙メニューに「Google のクライアント設定を読み込む…」→「Google に接続…」の順に並ぶ。
接続するとブラウザが開き、許可すると**そのまま1回目の同期が走る**。繋いだのに何も
出ないと、繋がったのか分からないため。

そのあとは右上の同期表示を押すか、`F5` で同期する。丸印の色が状態を表す
（緑＝同期済み、青＝同期中、黄＝一部を伝えられない、赤＝失敗、灰＝未接続）。
色だけに頼らせないよう、隣の文字にも同じ内容を出している。

右上に出すのは**同期の状態だけ**。操作の結果や断り書きを混ぜると、同期できているか
どうかが読み取れなくなる。

### トークンの守り方

`%LocalAppData%\Kado\google-tokens.dat` に、Windows の DPAPI
（`CurrentUser`）で暗号化して置く。**同じ PC の同じ Windows ユーザーでしか復号できない。**
ファイルごと別の PC へ写しても読めない。

守るべきはトークンのほう。クライアント ID とシークレットは、デスクトップアプリ型で
ある以上どのみち利用者の手元に置かれ、秘密として扱えない。対して更新トークンは、
これ1本でカレンダーとタスクを読み書きできてしまう。

認可のページは**既定のブラウザで開く**。アプリの中に埋め込まない。パスワードを入れる
場面なので、利用者がいつも使っているブラウザで URL を自分で確かめられるほうがよい。

### 同期しないもの

`local:` で始まる ID を持つカレンダーとタスクリストは同期しない。このアプリの中だけで
作ったもので、Google に行き先が無いため。Google から取り込んだものは Google 側の ID を
そのまま使う。

カレンダー一覧を取り込むとき、**チェックの状態と付け替えた名前は上書きしない**
（要件書 5.5）。同期のたびに戻ると使い物にならない。

### 繰り返しの例外回

Google は繰り返しを**親と例外回に分けて**持つ。親は `RRULE` だけを持ち、「この回だけ
時間を変えた」「この回は中止」は別のイベントとして流れてくる（`recurringEventId` が
親を指し、`originalStartTime` が本来の日）。

こちらは親の指定に `EXDATE` を混ぜて持つので、例外回を見たら**親からその日を除く**。
除かないと、同じ日に親の回と例外回が二重に出る。中止の回は除くだけで、予定としては
持たない。差し替えの回は除いたうえで、独立した予定として残す。

**例外回は必ず親のあとに処理する。** 相手が返す順番は決まっておらず、先に処理すると
そのあと親を取り込んだときに、足した除外日が上書きで消える。

親がこちらに無いこともある（差分で例外回だけが降ってきた）。そのときは除外だけ見送り、
例外回そのものは取り込む。落とすと予定が消えたように見える。次に親が降りてくれば、
その時点の例外回で除かれる。

### 色の扱い

番号（`colorId`）と実際の色の対応は `colors.get` から取る。こちらで書き写すと、
Google が色を調整したときに食い違う。取れなければ色の書き戻しだけを諦める。

こちらで変えたカレンダーの名前と色は相手へ送る。名前の付け替え（`summaryOverride`）も
表示色も Google では**その人だけの設定**なので、書き戻しても共有相手には影響しない。
送らないと、左パネルで色を変えても同期のたびに Google の色で戻る。

任意の `#rrggbb` はそのままは送れないので、**いちばん近い番号**に寄せる。近さは単純な
RGB の差ではなく、目の感じ方に合わせて緑を重く青を軽く見る。そのままだと、人が見て
遠い色が「近い」と判定されることがある。

### 二重起動を防ぐ

**2本動くと同期が壊れる。** どちらも同じデータベースを開き、同じカレンダーへ書き戻す。
片方が入れた予定をもう片方が知らないまま送り、差分の印も食い違う。

`Local\` 付きの Mutex で見張る。同じ Windows ユーザーのセッション内だけなので、共有 PC で
別の人が使っていても起動を妨げない。2本目は名前付きパイプで「前に出ろ」と伝えてから
静かに終わる。黙って終わると、押したのに何も起きないように見える。

### 裏での静かな同期

15分おきに走る。手で押したときと違い利用者が頼んでいないので、**失敗しても画面を
割り込ませない**。状態は右上の表示に出るので、気づける人は気づく。

繋がらない状態で叩き続けないよう、失敗のたびに間隔を倍にして2時間で頭打ちにする。
うまくいけば元の15分に戻る。警告どまり（一部を伝えられない）は繋がってはいるので、
間隔を伸ばす理由にしない。

例外が出ても止まらない。頼まれていない同期で落ちるのが、いちばん困る。

### まだ無いもの

**実際の Google にはまだ一度も繋いでいない。** API の呼び出しは、決まった応答を返す
HTTP と相手役の偽物で試しているだけ。認可・スコープ・実際の応答の形・呼び出し回数の
制限は、繋いでみるまで分からない。

繰り返しの例外回をこちらから作る道筋（画面で「この回だけ」を変える操作）はまだ無い。
取り込みと表示だけができる。

## 更新のしかた

`VoiceDock` と同じやり方にしてある。GitHub Releases の最新を見て、新しければ落として
入れ替える。

### 入れ替えの手順

**実行中の exe は Windows が掴んでいて上書きできないが、名前は変えられる。** この性質を
使う。

1. いまの exe を `.old` へ改名する
2. 落とした exe を元の場所へ置く
3. 新しいほうを `--after-update` 付きで起動する
4. こちらは終わる

途中で転んだら改名を戻し、元の版で動けるようにする。`.old` は次の起動で片付ける。

`--after-update` が要るのは、**前のプロセスがまだ終わりきっていない**ため。付けずに
起動すると二重起動の見張りに引っかかり、「すでに起動しています」で即座に終わって、
更新したのに立ち上がらないように見える。付いているときだけ30秒待つ。

Program Files のような書けない場所に置かれていると入れ替えられない。そのときはボタンを
押せなくして、リリースのページから手で差し替えてもらう。

### 落としてよい場所を確かめる

**落としたものはそのまま実行する。** だから応答に書かれた行き先を鵜呑みにしない。
HTTPS で、GitHub の配信先であることを確かめてから取りに行く。

`github.com.example.com` のような紛らわしいものを弾けることは試験で押さえてある。

ハッシュが付いていれば確かめる。付いていなければ、通信が HTTPS であることを頼りにする。

### 版の比べ方

**必ず数として比べる。** 文字で比べると `0.4.10` が `0.4.9` より古いことになり、
更新が止まる。`v0.5.0-beta` のような後ろ側は落として読む。

下書きと事前公開は配らない。

### いつ通信するか

確認するのは**起動したとき・常駐中の1日1回・⚙ →「更新を確認…」を押したとき**。
起動時は、最新なら何も出さない。毎回「最新です」と言われても邪魔なだけ。

### 自動更新（設定の「自動で更新する」。既定でオン）

新しい版を見つけたら裏で落とし、手が空いたときに入れ替える。落とす・SHA256 を照合する・
入れ替える・失敗したら戻す・再起動する部分は、手で更新するときと同じ
`UpdateService`／`ExecutableSwap` をそのまま使う。自動更新側（`Update/AutoUpdater`）が
持つのは、入れ替え待ちの控えと記録だけ。判断は通信も画面も時計も持たない
`Kado.Presentation.Update.AutoUpdatePolicy`・`StagedUpdateCheck` に寄せてあり、
`AutoUpdatePolicyTests`・`StagedUpdateTests` が固定している（時刻・操作の無い時間は引数で渡す）。

1. **見つけた** 起動時の確認と常駐中の確認で新しい版が見つかったら、画面を止めずに落とす
   （`TryStageInBackgroundAsync`）。⚙の「更新を確認…」で押したときだけは、これまでどおり
   更新の窓を出す
2. **落とした・照合した** 落とし先は、データの保存先の `updates\`（`%LOCALAPPDATA%\Kado\updates\`）。
   手で更新するときの置き場所（`%TEMP%\Kado\update`。起動のたびに片付ける）とは別にした。
   入れ替え待ちを**次の起動まで残す**ため。`DownloadAsync` が SHA256 を照合し、合わなければ消して
   例外にする。通ったものだけ、版・ファイルの場所・SHA256・リリースのページ・変更点の本文を
   設定（`update.staged`）に控える
3. **待っている** 1分おきの見回り（`AutoUpdatePolicy.PatrolInterval`）が、次を全部満たしたとき
   入れ替える。待たせている理由は、変わったときだけ `shell.log` に1行出す
   - メインウィンドウ以外の窓（編集画面・設定・更新の窓など）が開いていない。メッセージボックスのような
     WPF の窓ではないモーダルは、メインウィンドウが押せない状態（`IsWindowEnabled`）で見分ける
   - 右クリックのメニュー・ポップアップ（`PopupActivityHooks.Tracker`）とドラッグ（`DragActivity`）の最中でない
   - 同期の最中でない（`SyncViewModel.IsBusy`）
   - **10分以上、キーボードとマウスの操作が無い**（`GetLastInputInfo`。`Shell/UserIdle`。
     32ビットのミリ秒で約49日で一周するので、引き算は一周をまたいでも合う。取れなかったときは
     「手が空いた」とは言わない）
4. **入れ替えた** 入れ替える直前に、ファイルの有無・置き場所・版・SHA256 をもう一度確かめる
   （`StagedUpdateCheck.Evaluate`）。トレイに入っていた窓は、再起動のあとも前へ出さない
   （`--keep-hidden`。トレイのアイコンが出ているときだけ隠す）。ピン留め・スライド・窓の置き場所は、
   今までの更新の再起動と同じく、居かたが変わるたびに控えてあるので元どおりに戻る
5. **やめた** 入れ替えに失敗したら元の版へ戻し（`ExecutableSwap`）、その版の自動の入れ替えは
   止める（`update.auto_blocked_tag`。毎日同じ失敗を繰り返さない。手で更新するのは使える）

**終了するとき・次の起動** 入れ替え待ちがあるまま終了しても、終了の側では何もしない。次の起動の
最初（メインウィンドウを出す前。`ApplyStagedUpdateAtStartup`）に入れ替えて起動し直す。
Windows のサインアウト・シャットダウンで終わるときも終了の側は何もしないので、
`SessionEndWatcher` の流れを邪魔しない。控えたファイルが無い・SHA256 が合わない・
置き場所の外・控えの版がいまの版以下、のときは控えを捨てて普通に起動する。設定で切って
いるときも捨てる。

**更新したことの知らせ** 入れ替える直前に「入れ替えた版」を設定（`update.applied`）に控え、
新しい版の最初の起動で一度だけ、トレイのバルーンに「Kado を v1.1.2 に更新しました」を出す
（読んだら控えを消す。版がいまの版と違うときは出さずに捨てる）。押すと変更点の窓
（`UpdatedNoticeWindow`）が開く。本文は更新の窓と同じく Markdown として解釈せず文字のまま出す。
本文が取れていなかったときは「変更点はリリースのページをご覧ください」とリンク。
これは手で更新したときも同じ。

**手で更新するとき** 入れ替え待ちがある版なら、更新の窓は落とし直さず、その控えで入れ替える
（照合が通らなければ捨てて、これまでどおり落とす）。

**SHA256 が取れないときは自動にしない。** GitHub の API が回数の上限（403）で断られると、
配布物の URL を組み立てて落とす（`UpdateLinks`）。この経路は `digest`（SHA256）が API からしか
取れないので、照合できない。照合できないものを、利用者が気づかないまま実行しない。
そのため、`AutoUpdatePolicy.DecideDownload` は `DetailsUnavailable` かハッシュ無しを
`NoSha256` として落とさず、これまでどおりの通知（常駐中）・更新の窓（起動時）にする。
会社の共有回線ではこれが毎回起きるので、そこでは自動更新は働かず、手で「更新する」を押す今までの形になる。

そのほかに自動で落とさないのは、設定で切っているとき、exe のフォルダに書けないとき、
この版を前に入れ替えに失敗して止めてあるとき、もう控えてあるとき。落とせなかったときも
`shell.log` に残し、通知に戻す（次の確認でまた試す）。段階は `shell.log` に
`自動更新:` で始まる1行ずつ残る（見つけた・落とした・照合した・入れ替え待ちにした・待っている理由・
入れ替えた・やめた理由）。

### 見に行く先

見に行く先は `api.github.com/repos/Yu5rin/Kado/releases/latest`。リポジトリは公開して
いるので、認証なしで読める。

読めなかったとき（通信できない、公開済みのリリースが1つも無い、GitHub の回数制限に
かかった など）は、起動時の確認なら黙って見送り、⚙ →「更新を確認…」なら
「更新を確かめられませんでした」と出す。どちらもアプリの動きには差し支えない。

## 配布のしかた

`.github/workflows/release.yml` が Windows 向けの実行ファイルを作り、GitHub Releases に
上げる。`v0.4.0` のようなタグを押すと走る。タグを作らずに試したいときは、GitHub の
Actions 画面から「リリース」を手動実行すると、成果物（artifact）として14日間受け取れる。

**成果物には ZIP ではなく publish の中身をそのまま渡す。** GitHub は成果物を受け取る
ときに自動で ZIP にするので、こちらで ZIP にすると二重になり、落とした人が二度
展開することになる。ZIP を作るのは Releases へ添えるときだけ。

CI（`ci.yml`）は Linux で回していて、確認できるのはコンパイルが通ることまで。
リリースのほうは `windows-latest` なので、配布物を作る前に**テストを実際に実行**する。
この順序は落とせない。起動時にだけ落ちる WPF の書き方は Linux では気づけないため。

ただし、Windows で走るのも単体テストまでで、**画面を組み立てて動かしているわけではない**。
XAML の読み込みで落ちるかどうかは `XamlResourceTests` が静的に見ているだけなので、
リリース前に一度は手元で起動して確かめること。

配布物は自己完結（self-contained）の単一ファイル。.NET ランタイムを同梱するぶん
200MB 近くなるが、受け取る側でランタイムを入れずに済む。会社の PC のように勝手に
ランタイムを入れられない環境を想定している。

## 通知について

**通知は Phase 6 で、通知を出す仕組みごと作る。** それまで編集画面に通知の欄は置かない。

Google Calendar のイベントは `reminders` を持つので、項目としては揃っていない。
ただ、欄だけ先に付けると「設定したのに鳴らない」状態になる。欄が無いより悪い。

## 作業時間ブロック（`work_blocks`）は実装しないと決めた

要件書 5.4「タスクを時間軸へドラッグするとブロックが確保される」について。
テーブル・モデル・リポジトリのメソッド・描画の分岐まで一通り揃っていたが、
**作る導線（タスクを時間軸へドラッグする操作）が最後までひとつも実装されなかった**。
利用者と相談し、**この機能は実装しないと決定**。導線が無いぶんの画面側・
ViewModel 側・リポジトリ側のコードは落とした。

### 落としたもの

- `Data.Models.WorkBlock` レコード
- `TaskRepository` の `BlocksOf` / `BlocksInRange` / `UpsertBlock` / `DeleteBlock`
- `DeleteTaskEdit` が持っていた `blocks` の引数と、Undo での復元処理
  （タスクの削除・復元だけになった）
- `TimelineBuilder` の点線描画・ブロックの配置（`Layout` は予定だけを扱う）
- `TimeBlockViewModel` の `IsWorkBlock` / `TaskId`
  （予定の描画にも使う型なので、型自体は残した）
- `MainViewModel` の `EditBlock` / `DeleteBlockCommand` にあったブロック分岐
  （いまは時間軸の予定を開く・消すだけの単純な配線）
- `TimelineColumnView.xaml` のブロック用スタイル・コンテキストメニューの分岐

### 残したもの

- **テーブル定義**（`work_blocks`）。`SchemaMigrations` の V1 にそのまま残して
  ある。マイグレーションを増やしたくないため。読み書きするコードはもう無い
  ので、これ以上行が増えることは無いが、**過去の版で動いていた時期に作られた
  行が既存のデータベースには残っている可能性がある**
- `tests/Kado.Data.Tests/MigrationTests.cs` の `work_blocks` テーブルが
  作られることを確かめるテストと、外部キー制約のテスト（テーブルが残っている
  ことが仕様になったので、コメントを添えたうえでそのまま残した）

### 将来また作るなら

タスクを時間軸（週・日ビューの時間軸の列）へ落としたときの受け口は、
[`src/Kado.App/Views/TimelineColumnView.xaml.cs`](../src/Kado.App/Views/TimelineColumnView.xaml.cs)
の `OnColumnDropped` にある。いまはここに来た `TaskItem` を、終日レーンに
落としたとき（`DayView.xaml.cs` / `WeekView.xaml.cs` の `OnAllDayDropped`）と
同じ `MainViewModel.MoveTaskTo` へ流し、**期限を変えるだけ**にしている
（コメントに「タスクが持つのは期限で、時刻は持たない」とあるとおり、時間軸に
落ちても時刻を持たせていない）。

```csharp
// TimelineColumnView.xaml.cs, OnColumnDropped 内
case TaskItem task:
    main.MoveTaskTo(task.Id, column.Date, copy);
    break;
```

作るときは、まず `Data.Models` に `WorkBlock` を作り直し、`work_blocks`
テーブル（V1 に残したまま）に合わせてリポジトリの読み書きを用意する。そのうえで
`OnColumnDropped` を分け、「終日レーンへは期限を変える／時間軸の列へは
`WorkBlock` を確保する」にする。落とした Y 座標から時刻を割り出す
`TimeAt(...)` は同じファイルに既にある（予定の追加 `AddEventAt` が使っている）ので、
そのまま使える。所要時間は既定を決め打ちするか（例：30分）、編集画面で
直せるようにするかは未検討。

タスク側をドラッグの起点にする対応（右ペイン・スリムパネルの `TaskListItemViewModel`
の行に `DragSession.Current.DragIfMoved` を仕込む）も、あわせて要る。
月ビューの予定・終日レーンのドラッグ開始が同じ仕組みを使っているので、そこを参考にする。
