# Kado

[![CI](https://github.com/Yu5rin/Kado/actions/workflows/ci.yml/badge.svg)](https://github.com/Yu5rin/Kado/actions/workflows/ci.yml)

<img src="assets/icon.png" alt="Kado のアイコン" width="96">

**実働日で予定とタスクを管理する、Windows 向けのデスクトップアプリです。**

会社から配られる実働日（稼働日）カレンダーを取り込み、期限までの残りを「あと何日」ではなく
「残り 3実働日」のように数えます。画面の端に常駐させて一日中使うことを想定しており、
Google カレンダー／Google ToDo リストと同期できます。

## 主な特徴

- **実働日で数える。** 実働日データ（配布の Excel、または配信元の `feed.json`）を取り込むと、
  期限までの残り・遅れ・済んだタスクの結果（「2実働日 遅れて完了」など）を実働日で数えます。
  データの無い期間は暦日に切り替えます。設定で暦日で数えることもできます
- **マイルストーンと休業日を暦に出す。** 仕様期限などのマイルストーンは日付の行に、
  休業日・休日の特別出勤はマスの色で示します。祝日はアプリの中で計算するので、
  通信できない環境でも正しく出ます
- **実働日計算と工程逆算。** 期間の実働日数、基準日＋N実働日の到達日、納期から各節目の
  到達日を逆算する工程逆算を、実働日計算パネル（Ctrl＋K）で出せます
- **5つのビュー。** 一覧・年（年度単位、4月〜翌3月）・月・週・日。Ctrl＋ホイールで切り替えます
- **画面端に常駐する。** ふつうのウィンドウのほか、画面端にマウスを留めると出てくる
  「スライド」と、画面を分割して他のウィンドウと重ならないように留める「固定（ピン留め）」を
  選べます。左パネル・中央（カレンダー）・右パネルは個別に出し入れできます
- **Google と同期する。** Google カレンダーと Google ToDo リストを15分ごとに同期します。
  Google に繋がなくても、アプリの中だけのカレンダーで使えます
- **1行で入れる。** 「明日15時 打合せ @会議室A」のように打つと予定が入ります（クイック入力）
- **通知。** 予定の前と、朝にその日の予定と期限のタスクをまとめて知らせます（既定は切）
- **元に戻せる。** 追加・編集・削除・移動は Ctrl＋Z で戻せます。起動のたびに自動でバックアップを取ります

## 動作環境

- Windows 10 以降（64ビット）
- .NET を別に入れる必要はありません（実行に必要なものを配布物に同梱しています）
- Google と同期する場合は Google アカウント

## インストール

1. [Releases の最新版](https://github.com/Yu5rin/Kado/releases/latest) から
   `Kado-X.Y.Z-win-x64.exe` を落とします（`X.Y.Z` は版の番号）
2. 好きなフォルダに置いて起動します。インストーラーはありません

`.zip` は同じ中身をまとめたものです。展開先を自分で決めたいときに使います。

置き場所は、自分で書き込めるフォルダ（ドキュメントやデスクトップの下など）にしてください。
Program Files のような書き込めない場所に置くと、アプリから自分自身を更新できません。

アンインストールは、exe を消し、データの保存先（下の「データの保存場所」）を消せば済みます。

## 更新

起動したときに新しい版が出ていないかを確かめ、あれば案内の窓が出ます。
「更新する」を押すと新しい版を落として入れ替え、立ち上げ直します。

- 手で確かめるときは、設定の「Kado について」から「更新を確認…」を押します
- 起動時の確認は、設定の「起動と常駐」で切れます
- アプリから入れ替えられない場所に置いているときは、Releases から新しい exe を落として
  手で差し替えてください。データは exe とは別の場所にあるので、差し替えても消えません

## 使い方

### 画面

ふつうのウィンドウでは、左にミニ月暦とカレンダー一覧、中央にカレンダー、右に選んだ日の
予定とタスクが並びます。ツールバーの出しかたのボタンでウィンドウとスライドを切り替え、
ピンのボタンで画面端に固定します。どの出しかたでも Ctrl＋Alt＋C で前に出せます。

閉じるボタンではトレイに入り、裏で通知と同期を続けます（設定で「そのまま終わる」に
変えられます）。終了はトレイのアイコンを右クリックして「終了」から。

キー操作の一覧は歯車メニューの「ショートカット…」で見られます。

### 予定とタスクを入れる

- カレンダーのマスや時間帯をダブルクリックすると、その日（その時刻）で予定の追加が開きます
- 右パネルの「予定を追加」「タスクを追加」、またはクイック入力の欄に1行で打ちます。
  先頭に「todo」や「タスク」を付けるとタスクとして入ります
- 予定やタスクはドラッグで別の日へ移せます。Ctrl を押しながら落とすと複製します

### 実働日データを取り込む

歯車メニューの「実働日ファイルを取り込む…（Excel）」で配布の Excel を、
「配信元から実働日を取り込む」で設定した配信元の `feed.json` を取り込みます。
配信元の URL と1日1回の自動取得は、設定の「実働日」で決めます。

### Google と同期する

設定の「Google」から「Google に接続…」を押すと、既定のブラウザで Google の許可画面が
開きます。許可すると最初の同期が始まり、以後は15分ごとに同期します。
歯車メニューの「今すぐ同期」（F5）でいつでも同期できます。

配布物に Google の接続設定が入っていないときは、「Google に接続…」が押せません。
その場合は同じ画面の「自分のクライアント設定を使う…（JSON）」から、自分で発行した
クライアント設定を読み込みます。発行の手順は [`docs/google-setup.md`](docs/google-setup.md) にあります。

## データの保存場所

予定・タスク・実働日データ・設定・Google の接続情報は、すべて次のフォルダにあります。

```
%LOCALAPPDATA%\Kado
```

- 自動バックアップは同じフォルダの `backups` に、直近5本まで残ります
- 手で保存・復元するときは、設定の「データ」の「バックアップを保存…」「バックアップから復元…」を使います
- 異常終了したときの記録は同じフォルダの `crash.log` にあります

## 外部との通信

予定やタスクの中身を、作者や第三者のサーバーへ送ることはありません。通信するのは次の場合だけです。
詳しくは [プライバシーポリシー](site/privacy.html) をご覧ください。

| 通信先 | いつ |
|---|---|
| Google（カレンダー・ToDo リスト） | Google に接続しているとき。同期のため |
| Google ドライブ | 予定にファイルを添付したときだけ |
| GitHub（`api.github.com`） | 起動したときと「更新を確認…」を押したときに、新しい版を確かめる |
| GitHub（`github.com` ほか） | 「更新する」を押したときに、新しい版を落とす |
| 実働日データの配信元 | 配信元から取り込むとき、または自動取得を有効にしているとき（1日1回） |

### Phase 1 の実装範囲

`Kado.Core` の 5 クラスと、その単体テスト。UI はまだ作らない。
日付は `DateOnly` / `TimeOnly` を使い、`DateTime` は使わない。

#### WorkingDayCalendar

実働日の集合を保持し、判定と集計を行う不変オブジェクト。
稼働判定は `HashSet` による O(1)、範囲集計は昇順配列への二分探索で O(log n)。

```csharp
bool IsWorkingDay(DateOnly date);
bool HasDataFor(DateOnly date);          // 実働日データの登録範囲内か
int? IndexInMonth(DateOnly date);        // その月の何実働日目か。非稼働日は null
int CountInMonth(int year, int month);
IReadOnlyList<Milestone> MilestonesOn(DateOnly date);
```

稼働日は「登録された日付の集合」であって「土日祝を除いた日」ではない。
登録範囲外は土日祝から推測せず `HasDataFor` が false を返し、呼び出し側が暦日にフォールバックする。

#### WorkingDayMath

```csharp
int? CountBetween(DateOnly from, DateOnly to);        // 期間の実働日数
DateOnly? AddWorkingDays(DateOnly baseDate, int n);   // 基準日＋N実働日
DateOnly? PreviousWorkingDay(DateOnly date);
DateOnly? NextWorkingDay(DateOnly date);
```

境界規則は **`from` は数えず `to` は数える**。半開区間 `(from, to]` を数えると考えればよい。
この規則により `CountBetween(base, AddWorkingDays(base, n)) == n` が常に成り立つ（テストで担保）。

#### DueDateFormatter

```csharp
DueText Format(DateOnly due, DateOnly today);
```

| 条件 | 出力 |
|---|---|
| 実働日データがある範囲 | `残り 3実働日` |
| データが無い範囲 | `残り 189日` |
| 期限が今日 | `今日まで` |
| 期限を過ぎている | `3実働日 遅れ` |
| 期限日そのものが非稼働日 | `残り 2実働日（9/25まで）` |

**今日は数えず、期限日は数える。** データ範囲の内外が混在する場合は暦日側に倒す。

#### RecurrenceRule

指定文字列は **RFC 5545 の RRULE のサブセット**を採る。独自形式にしないのは、
Phase 4 の Google Calendar 同期でそのまま受け渡せるようにするため。

```
FREQ=DAILY;INTERVAL=2
FREQ=WEEKLY;BYDAY=MO,WE,FR
FREQ=MONTHLY;BYMONTHDAY=-1          … 月末
FREQ=YEARLY;BYMONTH=9;BYMONTHDAY=19
FREQ=WEEKLY;BYDAY=TU;UNTIL=20261231
```

対応種別は `RecurrenceRule.RegisterPattern` で後から足せる（要件書 11 章のとおり未確定のため）。

#### WorkdayFileImporter

会社配布 Excel の取り込み。**マイルストーン名称を固定 4 種で決め打ちしない。**
D 列に現れた文字列をそのまま種類として登録するので、将来の名称追加で壊れない。

**既存データは全置換しない。ファイルに含まれる期間だけを置き換える。**
稼働日とマイルストーンは期間が異なるため（実ファイルでは稼働日 2023/1/5〜2026/3/31、
マイルストーン 2025/1/10〜2026/3/26）、それぞれの期間で判定する。
この処理は `WorkingDayCalendar.Merge` にある。

不正な行は例外を投げず `ImportResult.Warnings` に積んで処理を続ける。

### 設計上の決定

仕様に明記が無く、実装で決めた点を挙げる。異論があれば作り直せる範囲に収めてある。

- **`AddWorkingDays` の負値**は「基準日より前の `|n|` 番目の実働日」。`PreviousWorkingDay(d)` と
  `AddWorkingDays(d, -1)` が一致する。基準日が非稼働日でも動く
- **`CountBetween` は `from > to` のとき負の値**を返す。向きを対称に扱えるようにした
- **超過していて期限が非稼働日の場合も寄せ先を明示する**（`2実働日 遅れ（9/18まで）`）。
  数字の根拠になる日が読めないと信用できないため
- **実働日換算で 0 日の超過だけ暦日に倒す**。今日が非稼働日で、寄せた期限との間に実働日が
  1 日も無いときに `0実働日 遅れ` となってしまうため、ここだけ `1日 遅れ（9/25まで）` とする
- **稼働日が 1 件も読めないファイルは例外**にする。行単位の不正は警告に留めるが、
  稼働日が皆無のファイルは実働日データとして成立しないため
- **ヘッダ行は警告にしない**。配布ファイルの B5 には見出しの文字列が入っている。
  データが始まる前の非日付セルは黙って読み飛ばし、データ開始後のものだけ警告する

### Phase 2 の実装範囲

`Kado.Data`。SQLite（Microsoft.Data.Sqlite + Dapper）でデータを保持し、
旧 Edge 拡張 inaCalendar のバックアップ JSON を取り込む。

#### スキーマ

版の記録には `PRAGMA user_version` を使い、各版をひとつのトランザクションで適用する。
一度リリースした版の SQL は書き換えない（既存のデータベースには適用済みで反映されないため）。

| テーブル | 内容 |
|---|---|
| `events` | 予定 |
| `tasks` / `work_blocks` | タスクと作業時間ブロック |
| `working_days` / `data_ranges` / `milestones` | 実働日データ |
| `settings` / `sync_state` | 設定と同期状態 |
| `tombstones` | 削除の伝播用 |

**予定とタスクは別テーブル**（要件書 3.1）。Google Calendar と Google Tasks が別 API である以上、
混ぜると同期のたびに変換が入り不整合の温床になる。

日付は `yyyy-MM-dd`、時刻は `HH:mm` の固定書式で持つ。辞書順と時系列が一致するので
`ORDER BY` や範囲検索がそのまま使える。書式はカルチャに依存させない。

検索用の FTS5 は Phase 6（検索）で追加する。マイグレーション機構があるので後から足せる。

#### 旧データの移行

`LegacyBackupImporter` が読み、`LegacyBackupMigrator` が書き込む。読み込みと保存を
分けてあるのは、取り込み内容を先に確認してから書き込めるようにするため。移行はやり直しが効かない。

**予定に付いていた ToDo フラグはタスクへ変換する**（要件書 8 章）。データモデルを分離した
ことによる唯一の変換処理なので、1 件ずつ変換ログに残す。

読めない行があっても止めない。1 件のために移行全体が失敗すると、どこまで移せたのか
分からなくなる。落とした行はログに残して先へ進む。

#### バックアップ

SQLite のオンラインバックアップ API を使う。**`VACUUM INTO` は使わない。**
メモリ上のデータベースに対して実行すると、例外も返り値のエラーも出さずに何も書き出さない。
黙って失敗されると、バックアップを取ったつもりで中身が無いという最悪の事態になる。

復元は接続を閉じてから行う。接続はプールに残ってファイルを掴み続け、WAL の内容が
本体に反映されるのもプールから外れたときなので、差し替える前に解放する。

### 開発フェーズ

計画時点の区切りを残しておくが、**現状はどの区分も実装済み**（詳細と、まだ手が
付いていない箇所は `docs/README.md` の「まだ実装していないところ」「まだ無いもの」を参照）。

| Phase | 内容 | 状態 |
|---|---|---|
| 1 | Core（繰り返し判定・実働日計算・期限カウント）＋単体テスト | 完了 |
| 2 | SQLite データ層＋旧 JSON インポート | 完了 |
| 3 | WPF ウィンドウモード＋予定・タスク CRUD＋Undo | 完了 |
| 4 | Google 同期（Calendar → Tasks の順） | 実装済み。実際の Google にはまだ一度も繋いでいない |
| 5 | Shell 統合（トレイ→サイドバー→ホバー→ピン／AppBar） | 実装済み。Windows 実機での確認は継続中 |
| 6 | 通知・フィード・祝日取得・バックアップ・年ストリップ・一覧ビュー | 実装済み |

Phase 5 は最重要要件（要件書 2 章）そのものであり最大の技術リスクだったため、
`samples/AppBarProbe` で成立性を先に確認してから本実装へ進んだ。
